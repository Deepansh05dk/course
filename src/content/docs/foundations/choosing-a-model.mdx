<Incident title="The leaderboard winner that lost" severity="SEV3">
A team switched their contract-extraction pipeline to the model at the top of a public leaderboard. Benchmarks said it was better. In production, extraction accuracy on *their* contracts dropped 6 points, latency doubled, and it wasn't available in the cloud region their enterprise customers required. They rolled back after two weeks.
</Incident>

**There is no "best model".** There's a best model *for your task, data, latency budget, cost budget and constraints*, and the only way to find it is to measure.

## The dimensions that matter

| Dimension | Questions to ask |
|---|---|
| **Quality on your task** | Does it pass *your* eval set? Public benchmarks are a starting filter, not an answer |
| **Latency** | What are TTFT and tokens/sec at your input sizes? With thinking on or off? |
| **Cost** | Per completed task, including retries, thinking and agent turns |
| **Context window** | Does your worst-case input fit with room for output? |
| **Capabilities** | Tool use, structured outputs, vision/PDF input, long output, caching, batch |
| **Data and compliance** | Retention terms, zero-data-retention options, regions, certifications (critical for FDE work) |
| **Availability** | Which clouds offer it (direct API, Bedrock, Vertex, Azure)? Rate limits for your tier? |
| **Lifecycle** | When will it be deprecated? How painful is migration? |

## The landscape in tiers

Names change every few months; the tiers don't.

| Tier | Strengths | Typical uses |
|---|---|---|
| **Frontier** (largest models from major labs) | Hardest reasoning, long agentic tasks, coding, nuanced writing | Agents, complex analysis, the "teacher" in evals |
| **Mid tier** | Strong quality at a lower price and latency | Most production chat, RAG answers, tool use |
| **Small / fast** | Very cheap, very fast | Classification, routing, extraction, high-volume pipelines |
| **Open-weight** (e.g. Llama, Mistral, Qwen, DeepSeek families) | Self-hostable, fine-tunable, full data control | Air-gapped or regulated environments, very high volume, custom fine-tunes |

:::tip[Start strong, then step down]
Prototype with a strong model to learn what's *possible*, build the eval, then try cheaper models against it. Starting with a weak model risks concluding "AI can't do this" when the model was simply too small.
:::

## Run a bake-off

A bake-off is a small, repeatable experiment: same inputs, several models, scored the same way.

```python
# evals/bakeoff.py
import json
import statistics
import time

import anthropic

client = anthropic.Anthropic(timeout=60.0)
MODELS = ["claude-opus-5-5", "claude-sonnet-5-5", "claude-haiku-5-5"]
CASES = [json.loads(line) for line in open("evals/triage_golden.jsonl")]
# each case: {"ticket": "...", "expected_category": "refund"}

SYSTEM = "Classify the support ticket into exactly one of: tracking, refund, damage, address_change, other. Reply with the category only."


def run(model: str) -> dict:
    correct, latencies, out_tokens = 0, [], []
    for case in CASES:
        start = time.perf_counter()
        msg = client.messages.create(
            model=model,
            max_tokens=2000,
            system=SYSTEM,
            messages=[{"role": "user", "content": case["ticket"]}],
        )
        latencies.append(time.perf_counter() - start)
        out_tokens.append(msg.usage.output_tokens)
        text = "".join(b.text for b in msg.content if b.type == "text").strip().lower()
        correct += text == case["expected_category"]
    return {
        "model": model,
        "accuracy": round(correct / len(CASES), 3),
        "p50_latency_s": round(statistics.median(latencies), 2),
        "p95_latency_s": round(statistics.quantiles(latencies, n=20)[-1], 2),
        "avg_output_tokens": round(statistics.mean(out_tokens)),
    }


for model in MODELS:
    print(run(model))
```

Then put the results in a decision table and add cost per 1K tasks from the [cost calculator](/foundations/cost-math/):

| Model | Accuracy | p95 latency | $ / 1K tickets | Verdict |
|---|---|---|---|---|
| Frontier | 0.96 | 4.1s | $18 | Ceiling: shows what's achievable |
| Mid | 0.95 | 2.3s | $9 | ✅ Best trade-off? |
| Small | 0.89 | 0.8s | $0.5 | Fails the 0.93 bar, unless used as a first-pass router |

*(The numbers above are illustrative. Your job is to produce real ones.)*

:::note[Bake-off hygiene]
Use **50–200 real examples**, including hard and weird ones. Run each model **more than once** (outputs vary). Report **p95**, not just averages. Fix the prompt *before* comparing models, and note that each model may need small prompt tweaks to be at its best.
:::

<ThinkFirst question="Acme wants Relay to (1) classify 9,000 tickets a week, (2) answer policy questions from documents, and (3) run an agent that issues refunds with approval. Would you use one model for all three? Explain your choice per feature.">

**Probably not one model. Pick per feature by task difficulty and stakes:**

1. **Classification:** start with a **small/fast** model. It's high volume, narrow, and easy to evaluate. Step up only if it fails your accuracy bar (or use it as a router with a fallback to a bigger model when it's uncertain).
2. **Policy Q&A (RAG):** a **mid-tier** model is often enough when retrieval is good. The answer quality depends more on retrieving the right chunks than on raw model power. Verify faithfulness with evals.
3. **Refund agent:** a **frontier or strong mid** model. It does multi-step reasoning with tool calls and real money at stake. Errors cost more than tokens.

Keep all three behind your `llm.py` and gateway so swapping models is a config change, and re-run the bake-off whenever a new model generation ships.

</ThinkFirst>

<Practice>

- **Warm-up:** write 30 labeled triage examples (`evals/triage_golden.jsonl`) from realistic logistics tickets, including 5 tricky ones (sarcasm, two issues in one ticket, other languages).
- **Stretch:** run the bake-off across three models from at least **two providers**. Produce the decision table with real numbers.
- **Boss level:** build a **cascade**: the small model classifies, but when it's unsure (it answers `other`, or a cheap self-check disagrees), escalate to the bigger model. Measure the accuracy and cost of the cascade against each single model. That's a result worth putting in your portfolio.

</Practice>
