## Errors: retryable vs not

| Error | Meaning | Retry? |
|---|---|---|
| Connection error, timeout | Network or provider slowness | ✅ with backoff |
| **429** rate limit | You exceeded your quota | ✅ with backoff, honouring `retry-after` |
| **529 / 503** overloaded, **500** | Provider-side trouble | ✅ with backoff, then fall back |
| **400** invalid request | Your request is wrong (too long, bad params) | ❌ Retrying the same request gives the same error |
| **401 / 403** | Bad key or no permission | ❌ Page someone |
| **404** | Model doesn't exist (or was retired) | ❌ Config bug |

## Backoff, jitter, and a retry budget

- **Exponential backoff:** wait 1s, 2s, 4s… so you stop hammering a struggling service.
- **Jitter:** randomize each wait so thousands of clients don't retry in sync (the "thundering herd").
- **Max attempts:** 2–3 is plenty for interactive requests. Users won't wait for 10.
- **Retry budget:** cap retries at a fraction of traffic (e.g. 10%). When the provider is truly down, retries only add load. Fail fast and fall back.
- **Timeouts:** set them per use case. Interactive: 20–60s, plus streaming so users see progress. Background jobs: longer.

The official SDKs already retry connection errors, 408, 409, 429 and 5xx with backoff (2 retries by default). Configure that **deliberately** rather than stacking your own retry loop on top. Stacked retries multiply: 3 × 3 = 9 attempts.

## The `complete()` function

```python
# app/llm.py
import logging
import time
from dataclasses import dataclass

import anthropic

from app.config import settings

log = logging.getLogger("relay.llm")

client = anthropic.Anthropic(
    timeout=settings.request_timeout_s,  # never rely on the long default for interactive paths
    max_retries=2,                        # SDK retries 429/5xx/connection errors with backoff
)


class LLMError(Exception):
    """A failure the caller should handle (show fallback UI, queue for a human, ...)."""


@dataclass
class Completion:
    text: str
    model: str
    stop_reason: str
    input_tokens: int
    output_tokens: int
    latency_s: float


def complete(
    messages: list[dict],
    *,
    system: str = "",
    model: str = settings.model,
    max_tokens: int = 4000,
    fallback_model: str | None = settings.fallback_model,
) -> Completion:
    start = time.perf_counter()
    try:
        msg = client.messages.create(
            model=model,
            max_tokens=max_tokens,
            messages=messages,
            **({"system": system} if system else {}),
        )
    except (anthropic.RateLimitError, anthropic.InternalServerError, anthropic.APIConnectionError) as exc:
        # The SDK already retried. Try a different model once, then give up cleanly.
        if fallback_model and fallback_model != model:
            log.warning("primary model failed (%s); falling back to %s", type(exc).__name__, fallback_model)
            return complete(messages, system=system, model=fallback_model,
                            max_tokens=max_tokens, fallback_model=None)
        raise LLMError("model unavailable") from exc
    except anthropic.NotFoundError as exc:
        # Wrong or retired model ID: a config bug. Page someone.
        log.error("model not found: %s", model)
        raise LLMError("model not found") from exc
    except anthropic.BadRequestError as exc:
        # Our bug (too long, invalid params). Retrying won't help.
        log.error("bad request to model: %s", exc)
        raise LLMError("invalid request") from exc

    if msg.stop_reason == "refusal":
        raise LLMError("model declined this request")

    text = "".join(block.text for block in msg.content if block.type == "text")
    if msg.stop_reason == "max_tokens":
        # Truncated output is a bug waiting to happen downstream. Make it loud.
        log.warning("output truncated at max_tokens=%s", max_tokens)

    result = Completion(
        text=text,
        model=msg.model,
        stop_reason=msg.stop_reason,
        input_tokens=msg.usage.input_tokens,
        output_tokens=msg.usage.output_tokens,
        latency_s=round(time.perf_counter() - start, 3),
    )
    log.info("llm_call", extra={"llm": result.__dict__})
    return result
```

Notice what the **caller** gets: either a `Completion` with metrics, or a single `LLMError` type to handle with a graceful fallback in the UI. Provider-specific exceptions never leak into the rest of the codebase.

:::note[Add `fallback_model` to settings]
Add `fallback_model: str | None = "claude-sonnet-5-5"` to `Settings`. A fallback from another **provider** is even more resilient. Module 11 moves this into a gateway.
:::

<ThinkFirst question="Relay's refund agent calls the model, which calls a `issue_refund` tool. The tool's HTTP request to Acme's payment API times out after 30s. Is it safe to retry? What do you need to make it safe?">

**Not automatically.** A timeout doesn't mean it failed. The payment API may have processed the refund and only the *response* was lost. A blind retry can refund twice.

To make retries safe:

1. **Idempotency keys:** send a unique key per logical refund (e.g. `refund:{ticket_id}:{amount}`). The payment API stores it and returns the original result on a duplicate request instead of acting again.
2. **Check before retrying:** query the refund status by that key first.
3. **Separate model retries from side-effect retries.** Retrying an LLM *call* is cheap and safe. Retrying an *action* needs idempotency.

This idea returns in Module 6 (durable agents) and Module 8 (tool safety).

</ThinkFirst>

- **Warm-up:** wrap your existing `llm.py` with the `complete()` above and write unit tests using a fake client that raises each error type. Assert the right behaviour for each one.
- **Stretch:** build a tiny **fault-injection proxy** (a FastAPI app that forwards to the provider but randomly returns 429, 529, or sleeps 40s). Point your client at it with `base_url` and watch your retries, timeouts and fallback work.
