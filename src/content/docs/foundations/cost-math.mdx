<Incident title="The $38,000 month" severity="SEV2">
A startup launched an "AI research assistant" with a $3,000/month estimate. The first invoice was $38,000. Causes, in order of impact: (1) the agent averaged 14 tool-call turns per task, re-sending the growing history every turn; (2) a bug retried failed requests forever; (3) one customer scripted 50,000 requests over a weekend. None of these were in the spreadsheet.
</Incident>

FDEs get asked "what will this cost?" in the **first meeting**. Applied AI Engineers get asked "why did this cost that?" after launch. Both questions come down to the same arithmetic.

## The formula

```text
cost per request = input_tokens  × input_price
                 + cached_tokens × cache_read_price      (much cheaper than input)
                 + output_tokens × output_price          (thinking tokens count here)

monthly cost     = cost per request × requests per month × multipliers
```

Two facts that surprise people:

1. **Output tokens cost about 5× as much as input tokens** on most models, so a verbose model is an expensive model.
2. **Price differences between tiers are huge**: often 20–40× between a frontier model and a small one. Model choice is your biggest cost lever, *as long as quality holds* (next lesson).

## Try it

Default values: 5,000 requests a day, a 3K-token prompt, a 400-token answer. Switch tiers, then raise the cached share to see what prompt caching does.

## The hidden multipliers

Spreadsheet estimates fail because they model **one clean request**. Production has multipliers:

| Multiplier | Typical size | Why |
|---|---|---|
| **Agent turns** | 3–20× | Each tool-call turn re-sends the whole conversation, so input grows every turn |
| **Retries** | 1.05–2× | Timeouts, 429s and validation repair loops repeat full requests |
| **Long tail inputs** | 2–5× on p95 | Your example was 1 page; real users paste 40 |
| **Thinking tokens** | 1–10× output | Reasoning is billed as output |
| **Evals and tests** | +5–30% | CI runs your eval set on every PR |
| **Abuse and bugs** | Unbounded | Scripts, loops, prompt-injection-driven tool spam |

:::caution[An agent's cost grows faster than its turn count]
If each turn adds about 2K tokens and the agent takes 10 turns, the inputs are 2K + 4K + … + 20K = **110K input tokens**, not 20K. History compaction, caching, and turn limits exist because of this.
:::

## Budget controls you should have from day 1

- **Log `usage` on every call**, and aggregate cost per feature, per customer, and per day.
- **Per-request caps:** `max_tokens`, a maximum number of agent turns, and a maximum retry count.
- **Per-user and per-tenant quotas** (requests and dollars per day).
- **Provider spend alerts and hard limits.**
- **An anomaly alert:** "today's cost is more than 2× the 7-day average."

<ThinkFirst question="Estimate Relay's monthly cost for ticket triage: 9,000 tickets a week, a 2,500-token system prompt + about 600 tokens per ticket, and a 300-token output. Pick a model tier from the calculator. Then name the two biggest risks to your estimate.">

**Rough maths** (about 39K tickets/month, 3.1K input and 300 output tokens each):

- Frontier tier ($4/$20 per M): input 3.1K × $4/M ≈ $0.0124, output 300 × $20/M = $0.006, so about **$0.018 per ticket and about $720/month**.
- Caching the 2.5K-token system prompt removes most of the input cost: about **$0.009/ticket, $350/month**.
- Small tier ($0.10/$0.50): about $0.0005/ticket, roughly **$20/month**, *if it passes your eval*.

**The biggest risks:**

1. **Thinking tokens and effort.** Reasoning can add hundreds or thousands of output tokens. Measure real `usage.output_tokens`.
2. **The long tail.** Some tickets are long email threads (p95 might be 5× the average), and retries and repair loops add more.

The point of the exercise: even at the frontier tier, this feature is cheap relative to 60 support agents' salaries. **Cost rarely kills a good triage feature; quality does.** Agent loops are where cost becomes dangerous.

</ThinkFirst>

<Practice>

- **Warm-up:** extend your `app/llm.py` (from Module 0) to compute and log cost per call using a price table in config.
- **Stretch:** write `scripts/cost_report.py` that reads `logs/calls.jsonl` and prints cost by day, by feature, and the p50/p95/max tokens per request.
- **Boss level:** build a **budget guard**: a per-user daily dollar limit stored in Redis or SQLite, checked before each call, returning HTTP 429 with a friendly message when exceeded. Write a test that simulates a script hammering the endpoint.
