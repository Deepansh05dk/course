## The problem: M × N integrations

Every AI application (chat app, agent, IDE assistant) needs access to tools and data (CRM, ticketing, databases, file systems). Without a standard, every app builds its own connector to every system: **M apps × N systems** integrations, each with its own bugs and security model.

The **Model Context Protocol (MCP)** is an open standard that turns that into **M + N**: each system exposes **one MCP server**, and each AI app implements **one MCP client**. Anthropic introduced it in late 2024, every major AI provider adopted it, and it was donated to the Agentic AI Foundation in December 2025. It's now named directly in GenAI and FDE job postings (see the [research](/research/)).

## The roles

| Role | What it is | Example |
|---|---|---|
| **Host** | The AI application the user interacts with | Relay, Claude Code, an IDE, a chat app |
| **Client** | The component inside the host that holds one connection to one server | Relay's connection to `acme-ops` |
| **Server** | A program that exposes capabilities over MCP | `acme-ops`, wrapping Acme's shipment API |

The **host** stays in control: it decides which servers to connect, which tools the model may see, and which calls need user approval.

## The three core primitives

| Primitive | Controlled by | What it is | Acme example |
|---|---|---|---|
| **Tools** | The **model** (it decides to call them) | Functions with a JSON Schema input, and optionally a structured output | `get_shipment(shipment_id)`, `create_claim(...)` |
| **Resources** | The **application** (it decides what to load) | Readable data identified by a URI, including templates | `acme://customers/C-2201`, policy documents |
| **Prompts** | The **user** (they pick one) | Reusable prompt templates with arguments | "Draft a delay apology for shipment X" |

Clients can also offer capabilities **to servers**: for example, letting a server ask the user for missing input (elicitation), or ask the host's model to generate text (sampling). You'll meet these in advanced servers; tools, resources and prompts cover most real integrations.

## Transports

| Transport | How | Use for |
|---|---|---|
| **stdio** | The host launches the server as a subprocess and talks over stdin/stdout | Local tools on a developer's machine (file systems, local databases, CLIs) |
| **Streamable HTTP** | The server is a web service at a URL (e.g. `https://mcp.acme.example/mcp`) | Remote, shared, production servers with authentication (lesson 4) |

:::note[The protocol is evolving]
MCP is versioned by date. The 2026-07-28 revision made the protocol **stateless** (clients discover servers instead of holding an initialized session), and the official SDKs negotiate older versions automatically. The **concepts** in this module (hosts, clients, servers, tools, resources, prompts, transports, auth) are stable. Check the current specification at modelcontextprotocol.io for wire-level details.
:::

<ThinkFirst question="Acme asks: 'Should we build an MCP server for our CRM, or just give Relay a Python function that calls the CRM API?' What do you recommend, and what decides it?">

**It depends on reuse and ownership:**

- **Just a function** if Relay is the only consumer, the integration is small, and the same team owns both. MCP adds a process boundary, deployment and auth that you don't need yet.
- **An MCP server** when **several AI applications** need the CRM (Relay, the sales assistant, engineers in Claude Code), when the **CRM team** should own the integration and its security (one place for permissions, rate limits and auditing), or when you want to plug the CRM into off-the-shelf hosts without writing code for each.

A good middle path: write the tool logic as **plain functions** in a shared package now, and wrap them in an MCP server when the second consumer appears. That's a few dozen lines (next lesson).

</ThinkFirst>
