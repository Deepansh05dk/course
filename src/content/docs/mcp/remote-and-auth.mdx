<Incident title="The service account that could see everything" severity="SEV1">
Acme's first remote MCP server for the CRM authenticated with one shared API key, and internally called the CRM with a super-user service account. Every connected AI app (and every user of those apps) could read every customer, including other business units' key accounts. An intern's Claude Code session pulled a competitor-sensitive account list into a notebook. The server was "authenticated". It just didn't know **who** was asking.
</Incident>

A local stdio server runs with the permissions of the person who launched it. A **remote** server is shared by many users and apps, so it must answer two questions on every request: **who is calling** (authentication) and **what are they allowed to do** (authorization).

## The OAuth roles in MCP

MCP's authorization model builds on OAuth 2.1. Map the roles:

| OAuth role | In MCP | At Acme |
|---|---|---|
| **Resource server** | The MCP server | `https://mcp.acme.example/mcp` |
| **Authorization server** | Your identity provider (IdP) | Acme's SSO (Okta, Entra ID, Auth0, Keycloak…) |
| **Client** | The MCP client inside the host | Relay, Claude Code, the sales assistant |
| **Resource owner** | The user | Jane, a support agent |

## An MCP server as a resource server

The v2 Python SDK supports this directly: you provide a **token verifier** (in production, JWT validation against your IdP) and auth settings. This example was run over HTTP for this lesson:

```python
# mcp_servers/acme_ops_remote.py: the same tools, served remotely, as an OAuth resource server
from mcp.server import MCPServer
from mcp.server.auth.middleware.auth_context import get_access_token
from mcp.server.auth.provider import AccessToken, TokenVerifier
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver.exceptions import ToolError

RESOURCE_URL = "http://127.0.0.1:8812/mcp"


class IdpTokenVerifier(TokenVerifier):
    """Validate tokens issued by Acme's identity provider (in production: verify the JWT
    signature, expiry, issuer, and that the audience is THIS server)."""

    async def verify_token(self, token: str) -> AccessToken | None:
        demo_tokens = {  # stand-in for JWT validation, for this local test only
            "tok-agent-jane": AccessToken(token=token, client_id="relay", scopes=["shipments:read"],
                                          subject="jane@acme.example", resource=RESOURCE_URL),
            "tok-other-audience": AccessToken(token=token, client_id="relay", scopes=["shipments:read"],
                                              subject="jane@acme.example", resource="https://other.example/mcp"),
        }
        return demo_tokens.get(token)


mcp = MCPServer(
    "acme-ops",
    token_verifier=IdpTokenVerifier(),
    auth=AuthSettings(
        issuer_url="https://login.acme.example",   # the authorization server clients get tokens from
        resource_server_url=RESOURCE_URL,          # this server's identity (token audience)
        required_scopes=["shipments:read"],
        validate_token_resource=True,              # reject tokens issued for a different server
    ),
)


@mcp.tool()
def whoami() -> str:
    """Return the authenticated user (demonstrates per-user context inside tools)."""
    token = get_access_token()
    if token is None:
        raise ToolError("Not authenticated")
    return f"{token.subject} via {token.client_id} with scopes {token.scopes}"


if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="127.0.0.1", port=8812, stateless_http=True)
```

What happened when we called it:

```text
$ curl -i -X POST http://127.0.0.1:8812/mcp  (no Authorization header)
HTTP/1.1 401 Unauthorized
www-authenticate: Bearer error="invalid_token", error_description="Authentication required", resource_metadata="http://127.0.0.1:8812/.well-known/oauth-protected-resource/mcp"

$ curl http://127.0.0.1:8812/.well-known/oauth-protected-resource/mcp
{"resource":"http://127.0.0.1:8812/mcp","authorization_servers":["https://login.acme.example"],"scopes_supported":["shipments:read"],"bearer_methods_supported":["header"]}

$ python test_client.py  (valid token, then a token for another server, then garbage)
valid token -> jane@acme.example via relay with scopes ['shipments:read']
tok-other-audience -> rejected: HTTP 401
garbage -> rejected: HTTP 401
```

| Request | Result |
|---|---|
| No token | `401`, with a pointer to the protected resource metadata (so clients can discover where to log in) |
| Valid token for this server | Tool runs; `get_access_token()` gives the tool the **user's identity and scopes** |
| Valid token issued for a **different** server | Rejected (`validate_token_resource=True`): the audience doesn't match |
| Garbage token | Rejected |

## Per-user authorization inside tools

Authentication tells you **who**; your tools must still decide **what they may see**:

- Use the token's subject (and groups or roles from claims) to scope every query: Jane sees her business unit's customers, nothing else (the same principle as permission-aware retrieval in Module 4).
- Check **scopes** per tool (`shipments:read` for lookups, `claims:write` for `create_claim`).
- Log every call with the user identity for auditing.

## The token-passthrough trap

The MCP server often has to call **upstream** APIs (the CRM). The tempting shortcut is to forward the token the client sent. Don't:

- That token's **audience** is the MCP server, not the CRM. Forwarding it breaks the audience model, and a server that accepts tokens meant for someone else can be abused.
- It creates a **confused deputy**: the upstream API can't tell which service is really acting, and policies, rate limits and audit trails stop meaning anything.

Instead, the MCP server calls upstream APIs with **its own credentials**, scoped down, passing the user's identity for authorization checks, or uses a proper **token exchange** with the IdP to get a token for the upstream API on the user's behalf.

## Operating a remote server

| Concern | Practice |
|---|---|
| **Transport security** | HTTPS only; for local HTTP servers, bind to localhost and keep the SDK's DNS-rebinding protection on |
| **Rate limits and quotas** | Per client and per user, to protect upstream systems from looping agents |
| **Statelessness** | The latest protocol revision is stateless, which makes horizontal scaling straightforward (stateless HTTP mode) |
| **Versioning** | Tool definitions change deliberately, with notice. Clients may pin and fingerprint them (lesson 6) |
| **Observability** | Per-tool latency, error rates, and calls per user and client (Module 9) |

<ThinkFirst question="Acme's IT security team asks: 'If we let Claude Code and Relay connect to our CRM MCP server, how do we know an AI isn't seeing data the user couldn't see themselves?' What do you answer, and what evidence would you offer?">

**The answer:** the AI acts **as the user**, never with more access than the user has.

1. **User-level OAuth through Acme's SSO:** every MCP request carries a token for that specific user, with scopes, issued by Acme's own identity provider. No shared keys.
2. **Audience-bound tokens:** tokens are issued for the CRM MCP server specifically and rejected elsewhere.
3. **Per-user authorization in every tool:** queries are filtered by the user's business unit and roles, exactly like the CRM's own UI.
4. **No token passthrough:** the MCP server calls the CRM with its own least-privilege credentials, enforcing the user's permissions itself.
5. **Audit logs:** every tool call is recorded with the user's identity, the arguments and the result status, available to the security team.

**Evidence:** an automated test suite with test users of different roles proving they can't see each other's data (including canary records), the negative audience test, and a sample of audit logs. Security teams trust tests and logs, not assurances.

</ThinkFirst>
