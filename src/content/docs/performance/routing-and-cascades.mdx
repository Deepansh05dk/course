<Incident title="The router that saved 60% and lost a customer" severity="SEV2">
To cut costs, Relay added a router: a small classifier sent "simple" tickets to the cheapest model and "complex" ones to the large model. Costs fell 60%. Six weeks later, Acme's largest customer escalated: their claims (long, multi-shipment, in German) were being labeled "simple" because they used plain language, and the cheap model was mishandling them. Nobody had evaluated the router itself, or sliced quality by customer.

Not every request needs your most capable model at maximum effort. But every attempt to save money by using less intelligence is a **quality decision**, and needs the same evidence as any other (Module 5).

## The levers, in order

Try them in this order. The early ones are simpler and keep one model:

| Lever | What you change | Typical effect | Watch out for |
|---|---|---|---|
| **1. Effort** | `output_config: {"effort": "low" \| "medium" \| "high" \| ...}` on the same model | Fewer thinking and output tokens on easy routes; often the best first move | Quality drops on hard tasks; measure per route |
| **2. Model per feature** | A smaller model for a whole feature (classification, extraction, short replies) | Large savings for well-defined tasks | Needs its own evals and prompt tuning |
| **3. Routing** | A classifier picks the model per request | Savings on mixed traffic | The router is a model too: its mistakes are silent |
| **4. Cascade** | Try the small model; escalate when a check fails | Near large-model quality at a fraction of the cost (when the check is good) | Escalated requests pay twice; latency rises for them |
| **5. Batch** | Asynchronous processing for work nobody waits on | 50% off on the Claude Message Batches API | Results take minutes to hours |

A useful default from practice: **before building a multi-model system, measure your strongest model at a lower effort level.** On current models, lower effort often matches what you'd get from a cascade, with one model, one prompt, one set of evals, and one prompt cache. That last point matters: **caches are per model**, so every model in a router or cascade warms its own cache, and a request escalated to a second model reads nothing from the first one's cache.

## Routing vs cascades

<Diagram
	caption="A router decides before any model runs. A cascade decides after the cheap model has answered, using a check on that answer."

A cascade is only as good as its **check**. Good checks are cheap and objective: the output validates against the schema, every claim cites a retrieved passage (Module 4), the classification falls into a known category with no "other", a code check passes. "Ask the small model how confident it is" is weak: models are often confidently wrong.

```python
"""Model cascade: try the small model first; escalate when a check says the answer isn't good enough."""
from dataclasses import dataclass
from typing import Callable


@dataclass
class Result:
    answer: str
    model: str
    cost_usd: float
    escalated: bool


def cascade(
    ticket: str,
    small: Callable[[str], tuple[str, float]],     # returns (answer, cost)
    large: Callable[[str], tuple[str, float]],
    accept: Callable[[str, str], bool],            # a cheap check: schema valid? grounded? confident?
) -> Result:
    answer, cost = small(ticket)
    if accept(ticket, answer):
        return Result(answer, "small", cost, escalated=False)
    better, extra = large(ticket)                   # you pay for both calls on escalation
    return Result(better, "large", cost + extra, escalated=True)
```

Simulated on 20,000 tickets, with assumed accuracies (80% easy tickets; the check catches 70% of bad small-model answers and wrongly flags 5% of good ones):

```text
always small  accuracy  88.1%   cost per 1,000 tickets $  0.30
always large  accuracy  95.3%   cost per 1,000 tickets $  6.00
cascade       accuracy  95.4%   cost per 1,000 tickets $  1.07
escalated: 12.9%
```

Under these assumptions, the cascade matches the large model's accuracy at **18% of its cost**. Before you believe numbers like that for your system, notice what the simulation assumed: the small model's errors, the large model's errors and the check's misses are **independent**. In reality they're correlated: the tickets that fool the small model are often the ones that fool the check, and that the large model also finds hard. Measure all three on real data.

## Batch processing: half price for patience

Lots of AI work has no user waiting: nightly ticket classification, re-embedding documents, generating summaries for yesterday's calls, running eval suites. The **Message Batches API** processes requests asynchronously at **50% of the normal price**: up to 100,000 requests (or 256 MB) per batch, most finishing within an hour, at most 24 hours, with results available for 29 days.

```python
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()

batch = client.messages.batches.create(
    requests=[
        Request(
            custom_id=ticket.id,                  # results come back in any order: key by this
            params=MessageCreateParamsNonStreaming(
                model="claude-haiku-5-5",
                max_tokens=256,
                system=TRIAGE_PROMPT,
                messages=[{"role": "user", "content": ticket.text}],
            ),
        )
        for ticket in yesterdays_tickets
    ]
)
# Later (a scheduled job, not a sleeping web request):
# client.messages.batches.retrieve(batch.id).processing_status == "ended"
# for result in client.messages.batches.results(batch.id): ...
```

Batches combine with prompt caching (a shared system prompt across the batch). They're single-shot: no tool loops inside a batch. On cloud platforms, the Claude Message Batches API isn't available everywhere; Bedrock and Vertex AI have their own batch inference offerings.

<ThinkFirst question="Relay has three workloads: (a) live chat with customers, (b) triage of incoming emails into 12 categories, (c) a nightly summary of every claim filed that day for the claims team. Which cost levers would you try for each, in which order?">

- **(a) Live chat:** prompt caching first (lesson 1). Then try a lower effort level on the current model, measured with the chat eval suite. Routing is risky here (conversations change difficulty mid-way) and cascades add latency a user feels, so they come last, if at all.
- **(b) Email triage:** a well-defined classification task, so a **small model per feature** is the natural candidate. Validate it against labeled data, and add a cascade with an objective check: escalate when the small model returns "other" or a low-agreement label. If triage can wait a few minutes, batch it.
- **(c) Nightly summaries:** nobody is waiting, so the **Batch API** (50% off) is an easy win, combined with prompt caching for the shared instructions. Model choice here follows quality evals: summaries are what claims handlers read every morning.

</ThinkFirst>

<Practice>

- **Warm-up:** run Relay's eval suite on your main model at two lower effort levels. Record quality, output tokens and latency per level.
- **Stretch:** build a cascade for email triage with an objective check, and measure escalation rate, accuracy and cost on 200 labeled emails, against the large model alone.
- **Boss level:** move one Relay workload that nobody waits on to the Batch API, with a scheduled job, idempotent result processing keyed by `custom_id` (Module 6), and a cost comparison before and after.
