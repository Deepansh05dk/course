<Incident title="The greeting that cost 40,000 dollars" severity="SEV3">
Relay's prompt caching had cut input costs by 70%. In March, a product manager asked for friendlier answers, and an engineer added one line to the top of the system prompt: `f"Today is {date}. The customer's name is {name}."`. Every test passed, and the answers were friendlier. Nothing errored. But the cache hit rate fell from 92% to 3%, and the monthly bill rose by 40,000 dollars. Nobody noticed until the quarterly cost review, because nothing was monitoring `cache_read_input_tokens`.
</Incident>

Most production prompts are mostly **the same** from request to request: the tool definitions, the system prompt, the policies, the few-shot examples. Only the end changes. **Prompt caching** lets the provider keep the processed form of that shared beginning, so later requests read it back instead of processing it again.

The result: cached input tokens cost about **a tenth** of the normal price (less on some models), and responses start faster because the cached part doesn't need to be processed again. For most AI products it's the largest single cost reduction available, and unlike the levers in the next lessons, it doesn't trade away any quality.

## How it works: a prefix match

<Diagram
	caption="The request renders in a fixed order: tools, then system, then messages. The cache matches the longest identical prefix up to a breakpoint. One changed byte invalidates everything after it."
	code={`flowchart LR
    T["tools<br/>2K tokens"] --> S["system prompt<br/>+ policies<br/>10K tokens"]
    S --> BP(["cache breakpoint"])
    BP --> D["retrieved docs<br/>3K, per question"]

The rules that follow from "prefix match":

1. **Order matters.** The render order is `tools` → `system` → `messages`. Put stable content first and volatile content last.
2. **Any byte change invalidates everything after it.** A timestamp, a reordered JSON key, a different tool order, a user name.
3. **You mark where caching ends** with a `cache_control` breakpoint (up to four per request), or use **automatic caching**, which places the breakpoint on the last cacheable block for you.
4. **There's a minimum length.** Prefixes shorter than the model's minimum (512 tokens on the newest Claude models, more on some older ones) silently don't cache.
5. **Entries expire.** The default lifetime is 5 minutes, refreshed for free on every read; a 1-hour option exists for traffic with longer gaps.
6. **Caches are scoped** to a model and to your workspace or organization. Switching models means a cold cache.

## In code

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=2000,
    tools=sorted_tools,                      # deterministic order: tools render first
    system=[{
        "type": "text",
        "text": RELAY_INSTRUCTIONS_AND_POLICIES,   # frozen: no dates, names or IDs in here
        "cache_control": {"type": "ephemeral"},    # breakpoint: cache everything up to here
    }],
    messages=[{"role": "user", "content": f"<docs>{retrieved}</docs>\n\n{question}"}],  # volatile part last
)

u = response.usage
print(u.cache_creation_input_tokens, u.cache_read_input_tokens, u.input_tokens)
```

The three usage fields are your ground truth:

| Field | Meaning | Price (multiple of normal input) |
|---|---|---|
| `cache_creation_input_tokens` | Written to the cache this request | 1.25× (5-minute TTL), 2× (1-hour TTL) |
| `cache_read_input_tokens` | Read from the cache | ~0.1× (0.05× on Claude Opus 5.5) |
| `input_tokens` | Processed normally (after the last breakpoint) | 1× |

So with the 5-minute TTL, a prefix pays for itself on the **second** request: 1.25 + 0.1 = 1.35 versus 2.0 without caching. For multi-turn conversations and agent loops, automatic caching (a top-level `cache_control`) moves the breakpoint forward as the conversation grows, so each turn reads everything before it.

## Find what's breaking your cache

Code review rarely spots cache breakers, because each one looks harmless. A more reliable method: **render consecutive requests and find where they first differ.** This small auditor does exactly that (tested on a "bad" and a "good" version of Relay's request builder):

```python
"""Find what breaks prompt caching: diff the rendered prefix of consecutive requests."""
import json


def render(request: dict) -> str:
    # The cache is a prefix match over tools -> system -> messages, in that order.
    parts = [request.get("tools", []), request.get("system", ""), request.get("messages", [])]
    return json.dumps(parts, ensure_ascii=False)


def shared_prefix(a: dict, b: dict) -> tuple[int, int, str]:
    ra, rb = render(a), render(b)
    n = 0
    while n < min(len(ra), len(rb)) and ra[n] == rb[n]:
        n += 1
    return n, len(rb), rb[max(0, n - 30):n + 40]  # where the two requests diverge


def audit(requests: list[dict]) -> None:
    for prev, cur in zip(requests, requests[1:]):
        n, total, around = shared_prefix(prev, cur)
        print(f"  reusable prefix: {n / total:5.1%} of {total} chars | diverges at: ...{around}...")
```

The bad builder's requests diverge at the timestamp in the system prompt, and then at the very first byte, because the tool order changed. The good builder shares 99% of every request. It moved the date and the user into the user message, after the cached prefix, and sorted the tools.

The usual suspects:

| Pattern | Why it breaks caching |
|---|---|
| `datetime.now()` or a request ID in the system prompt | The prefix is unique per request |
| The user's name, plan or locale in the system prompt | One cache entry per user, which usually expires before it's reused |
| Tools built from a `set`, a dict from an unordered source, or a per-user tool list | Tools render first, so nothing after them matches |
| `json.dumps` without `sort_keys=True` in prompt content | Different key order, different bytes |
| Conditional sections (`if flag: system += ...`) | Every combination of flags is a different prefix |
| Switching models, or changing thinking/effort settings per request | Caches are per model; thinking settings can invalidate parts of the cache |

On the Claude API there's also a **cache diagnostics** feature (beta) that reports server-side where two consecutive requests diverged, so you don't have to log and diff the payloads yourself.

## Verify continuously

The most expensive caching failure is **silent**: the requests keep succeeding and only the bill grows, like in the incident above. Make it impossible to miss:

- **A dashboard and an alert** on the cached share: `cache_read_input_tokens / (cache_read + cache_creation + input_tokens)`, per feature (Module 9).
- **An integration test** that sends the same prefix twice and asserts `cache_read_input_tokens > 0` on the second request. Run it in CI whenever prompt-assembly code changes.
- **A code-review rule:** nothing dynamic before the breakpoint.

<ThinkFirst question="Relay's agent sends a 14,000-token prefix (tools + system + policies) and has 25 turns per conversation on average. Each turn adds ~1,500 tokens. Roughly what share of its total input tokens could caching serve from cache, and what one design decision protects that number?">

Total input over 25 turns: each turn sends the prefix plus the history so far, so about 25 × 14,000 + 1,500 × (0 + 1 + … + 24) = 350,000 + 450,000 = **800,000 tokens**. With automatic caching, each turn reads everything the previous turn sent and only processes the newly appended ~1,500 tokens (plus the write premium on them). New tokens total about 14,000 + 25 × 1,500 ≈ 51,500, so roughly **94% of input tokens** can come from cache.

The decision that protects it: **the conversation is append-only**. Never edit or reorder earlier turns, never change the tools or the system prompt mid-conversation, and never vary thinking or effort settings per turn. Any of those rewrites the prefix and turns cheap reads back into full-price writes.

</ThinkFirst>
