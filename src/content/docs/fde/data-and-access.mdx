In your own company, data access is a ticket. At a customer, it's a **process**, owned by people with good reasons to be careful, and it's usually the longest lead time in an engagement. FDEs who treat access and security as first-class work, starting on day one, ship months earlier.

## Legacy systems

Most valuable data lives in systems that were never designed for AI: mainframes, old databases, SOAP services, desktop apps, spreadsheets on shared drives. Typical patterns, from least to most invasive:

| Pattern | When |
|---|---|
| **Exports** (nightly files, read replicas) | Fastest start; fine for POCs and data that can be a day old |
| **Existing APIs**, even old ones, wrapped as task-shaped tools (Module 7) | The usual production answer |
| **Database read access** through views the owner controls | When there's no API; views keep the owner in control of what's exposed |
| **Change data capture / events** | Freshness matters and the system can publish changes |
| **UI automation** (computer use, RPA) | A last resort when there's truly no other way; fragile, so contain it and monitor it closely |

Respect the system's limits: a 15-year-old database may not survive an agent issuing 50 queries per conversation. Cache, rate-limit and batch (Modules 7 and 10).

What this usually means for you:

- **You deploy into their environment**, with their CI/CD, their secrets manager, their logging. Build for portability from the start (Module 11): containers, configuration by environment, the client factory.
- **No public internet path** for data. Model access through the platform route they've approved, often with private connectivity.
- **Their identity system:** users log in with the company's SSO; your service acts with the user's permissions (Modules 4 and 7).
- **Limited access for you:** you may get a locked-down laptop, a jump host, or work through their engineers. Plan for slower iteration and invest in good local test setups with synthetic data.

## Getting through security review

Security teams have seen many vendors over-promise. What gets you through:

1. **Start early**, and ask for their process and questionnaire in week one.
2. **Bring a clear data-flow diagram** (like the one above) and a threat model (Module 8).
3. **Answer with evidence**, not assurances: test results for permission isolation, the red-team suite's results, sample audit logs.
4. **Offer a staged scope:** read-only first, no customer-facing actions, redacted data for evals. Expand once trust exists.
5. **Name an owner** for each open item, and keep a shared tracker. Security reviews stall on unanswered questions, not on "no".

<ThinkFirst question="Day one at a new customer. Write the checklist of requests you send in your first email, so the slow things start immediately.">

1. **People:** the sponsor, the process owner, 3–5 users to shadow, the IT contact for each system, and the security and data-protection contacts.
2. **Security process:** their vendor or AI security questionnaire, the review process and its calendar (boards that meet every two weeks matter).
3. **Access requests** for each system in the audit, starting with the slowest owner. Ask what the request process is, not just for access.
4. **Environments:** where we deploy (their cloud account, network, CI/CD), how model access is approved (which platform, region), and the dev/test environment.
5. **Data handling rules:** where customer data may be processed and stored, retention, and whether redacted samples can be used for evals.
6. **Baseline data:** whatever they already measure for the target workflow (handle times, volumes), so the baseline (lesson 2) can start now.

Then put every request in a shared tracker with an owner and a date, and review it in every status meeting.

</ThinkFirst>
