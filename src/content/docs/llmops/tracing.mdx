A single AI request can involve several model calls, retrieval, a handful of tools, retries and a fallback. A log line per request tells you **that** something was slow or wrong. A **trace** tells you **where** and **why**.

## Traces, spans and the agent tree

A **trace** is the full story of one request. It's made of **spans**: timed operations with a name, a parent, a status and attributes. For an agent, the spans form a tree:

## OpenTelemetry and the GenAI semantic conventions

**OpenTelemetry (OTel)** is the vendor-neutral standard for traces, metrics and logs. Its **GenAI semantic conventions** define standard span names and attributes for model calls, agents and tools, so any OTel-compatible backend can understand your traces. They are still marked "Development" (names can change), and in 2026 they moved into their own repository, but the core is widely used:

| Span | Name format | Key attributes |
|---|---|---|
| Model call | `chat {model}` | `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.response.finish_reasons`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens` |
| Agent run | `invoke_agent {agent}` | `gen_ai.agent.name`, `gen_ai.conversation.id` |
| Tool call | `execute_tool {tool}` | `gen_ai.tool.name`, `gen_ai.tool.call.id` |
| Any failure | | `error.type`, plus span status `ERROR` |

Two details from the spec that are easy to get wrong:

- `gen_ai.usage.input_tokens` should include **all** input tokens, cached ones too. Anthropic's API reports cache reads and writes **separately** from `input_tokens`, so you add them back.
- **Message content is opt-in.** Instrumentations shouldn't capture prompts and responses by default, because they routinely contain customer data. More on that below.

## Instrumenting Relay

Three small helpers wrap the agent run, each model call, and each tool call. They plug into the Module 6 agent loop:

```python
"""OpenTelemetry tracing for LLM and tool calls, using the GenAI semantic conventions."""
import json
from contextlib import contextmanager

from opentelemetry import trace
from opentelemetry.trace import SpanKind, Status, StatusCode

tracer = trace.get_tracer("relay")

PRICES = {"claude-sonnet-5-5": (2.00, 10.00)}  # USD per million input / output tokens


@contextmanager
def agent_span(agent_name: str, conversation_id: str, **attrs):
    with tracer.start_as_current_span(f"invoke_agent {agent_name}", kind=SpanKind.INTERNAL) as span:
        span.set_attributes({
            "gen_ai.operation.name": "invoke_agent",
            "gen_ai.provider.name": "anthropic",
            "gen_ai.agent.name": agent_name,
            "gen_ai.conversation.id": conversation_id,
            **attrs,  # your own dimensions: tenant, feature, prompt version...
        })
        yield span


def traced_chat(client, **request):
    model = request["model"]
    with tracer.start_as_current_span(f"chat {model}", kind=SpanKind.CLIENT) as span:
        span.set_attributes({
            "gen_ai.operation.name": "chat",
            "gen_ai.provider.name": "anthropic",
            "gen_ai.request.model": model,
            "gen_ai.request.max_tokens": request["max_tokens"],
        })
        try:
            response = client.messages.create(**request)
        except Exception as e:
            span.set_attribute("error.type", type(e).__name__)
            span.set_status(Status(StatusCode.ERROR, str(e)[:200]))
            raise
        usage = response.usage
        cache_read = usage.cache_read_input_tokens or 0
        cache_write = usage.cache_creation_input_tokens or 0
        price_in, price_out = PRICES.get(model, (0, 0))
        span.set_attributes({
            "gen_ai.response.id": response.id,
            "gen_ai.response.model": response.model,
            "gen_ai.response.finish_reasons": [response.stop_reason or "unknown"],
            # The spec counts ALL input tokens; Anthropic reports cached ones separately, so add them back.
            "gen_ai.usage.input_tokens": usage.input_tokens + cache_read + cache_write,
            "gen_ai.usage.cache_read.input_tokens": cache_read,
            "gen_ai.usage.output_tokens": usage.output_tokens,
            "relay.cost_usd": round((usage.input_tokens * price_in + cache_read * price_in * 0.1
                                     + cache_write * price_in * 1.25 + usage.output_tokens * price_out) / 1e6, 6),
        })
        return response


def traced_tool(name: str, call_id: str, handler, args: dict):
    with tracer.start_as_current_span(f"execute_tool {name}", kind=SpanKind.INTERNAL) as span:
        span.set_attributes({
            "gen_ai.operation.name": "execute_tool",
            "gen_ai.tool.name": name,
            "gen_ai.tool.call.id": call_id,
            "relay.tool.args_size": len(json.dumps(args)),  # sizes, not contents: arguments may hold PII
        })
        try:
            result = handler(**args)
        except Exception as e:
            span.set_attribute("error.type", type(e).__name__)
            span.set_status(Status(StatusCode.ERROR, str(e)[:200]))
            return {"content": f"Error: {e}", "is_error": True}
        span.set_attribute("relay.tool.result_size", len(str(result)))
        return {"content": str(result), "is_error": False}
```

## What to capture, and what not to

| Capture | Why |
|---|---|
| Model, parameters, token counts, cost, finish reason | Cost and quality analysis; spotting `max_tokens` truncation |
| Latency per span, time to first token | Finding the slow part |
| Tool names, call IDs, status, **sizes** of arguments and results | Debugging agents without storing data |
| Your dimensions: tenant, feature, **prompt version**, model route, experiment arm | Slicing dashboards; comparing versions (lesson 2) |
| User ID (hashed or pseudonymous) | Per-user debugging and abuse detection |

| Be careful with | Approach |
|---|---|
| **Prompts and responses** | Off by default. Where you need them (debugging, building eval sets), capture them **redacted** (Module 8), with restricted access, a retention limit, and sampling |
| Tool arguments and results | Same: sizes and statuses by default, contents only with redaction and access control |
| Secrets | Never. Scrub headers and environment values in your exporters |

## Where traces go

| Tool | Type |
|---|---|
| **Langfuse** | Open-source LLM observability (self-host or cloud): traces, prompt management, evals, datasets; OTel-based SDK |
| **Arize Phoenix** | Open-source tracing and evaluation, built on OTel and the OpenInference conventions |
| **LangSmith** | LangChain's hosted tracing and evaluation platform; works without LangChain too |
| **General observability** (Datadog, Grafana/Tempo, Honeycomb, New Relic…) | Ingest OTel GenAI spans next to the rest of your system's traces |

Because you instrument with OpenTelemetry, you can switch backends without touching your code. That matters in FDE work: the customer's existing observability stack often decides the backend.

<ThinkFirst question="Look at the trace above. Name two concrete improvements to Relay that the trace suggests, and how you'd confirm each worked.">

1. **The two tools in the first turn ran one after the other** (`get_shipment`, then `search_policies`), though the model requested them together. Running them **in parallel** (Module 6) saves about 90 ms here, more with slower tools. Confirm: the two tool spans should overlap in time in new traces.
2. **`get_customer_overview` took 1.4 s and then failed** (a CRM timeout), and the model had to answer without it. Options: a shorter timeout with a cached fallback, or fetching the customer overview **before** the agent starts (it's needed in almost every conversation). Confirm: the error rate on that span, and p95 latency of the whole trace, on the dashboard (lesson 4).

Also visible: the final answer took 2.1 s for 318 output tokens. If that's user-facing, make sure it **streams** (Module 1) so time to first token stays low.

</ThinkFirst>
