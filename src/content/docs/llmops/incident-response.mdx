<Incident title="The answer that went viral" severity="SEV1">
On a Saturday, a customer posted a screenshot: Relay had told them Acme would "always refund 150% of the shipment value for any delay". It was wrong (the model had merged two policy passages), and the post was spreading. The on-call engineer had no runbook for "the AI is saying something wrong", no way to turn off one feature without turning off the whole chat, and no idea how many other customers had received the same answer. It took four hours to find out: 23.
</Incident>

AI features fail in all the usual ways (outages, latency, bugs) and in some new ones. Your incident process needs to cover both.

## The kinds of AI incidents

| Type | Example | First lever |
|---|---|---|
| **Availability** | Provider outage, rate limits, timeouts | Fallback route (lesson 3), degraded mode |
| **Quality** | Wrong answers, hallucinated policy, broken formatting after a deploy | Roll back the AI config (lesson 2); disable the feature |
| **Safety and security** | Prompt leak (canary hit), injection exploited, harmful output, data from another tenant | Kill switch, revoke tools, preserve evidence, involve security (Module 8) |
| **Cost** | Looping agent or batch job, cache broken (Module 10) | Gateway budget cut-off, pause the job |
| **Action** | Agent took a wrong real-world action (refund, email) | Stop the agent, reverse actions, reconcile (Module 6) |

## Levers you need before the incident

The worst time to build a kill switch is during the incident. Have these ready:

| Lever | What it does |
|---|---|
| **Per-feature kill switch** | Turns one AI feature off (via a feature flag) without a deploy, showing a graceful fallback ("Our assistant is unavailable; here's how to reach support") |
| **Tool revocation** | Removes one tool (for example `issue_refund`) from all agents instantly, keeping the rest working |
| **Config rollback** | Switches to the previous AI config version in seconds (lesson 2) |
| **Degraded modes** | Read-only agent, retrieval-only answers with citations and no generation, or "drafts only, human sends" |
| **Blast-radius queries** | Saved queries over traces: "which conversations got an answer containing X?", "which tenants were affected between T1 and T2?" |
| **Customer communication templates** | Pre-approved wording for status pages and account managers |

## Runbooks

A runbook is a short, specific guide for one alert or incident type, written in advance for a tired person at 3 a.m. Each alert from lesson 4 links to one. A good AI runbook includes:

1. **What this alert means** and how users are affected.
2. **Dashboards and saved trace queries** to look at first.
3. **Containment levers**, in order, with exact commands or flag names.
4. **Who to involve:** security for canary hits and data exposure, the account team for enterprise customers, legal for data incidents.
5. **How to verify recovery.**

## Blameless post-mortems

After the incident, write a **post-mortem** within a week. **Blameless** means it assumes people acted reasonably with the information and tools they had, and looks for the **system** changes that would have prevented or shortened the incident. If the answer is "someone should have been more careful", the system still allows the same mistake.

A template that works well for AI incidents:

```markdown
# Post-mortem: <title>                                  Severity: SEV2

## Summary
Two or three sentences: what happened, impact, duration.

## Impact
Users/tenants affected, wrong answers or actions (with counts from traces), cost, customer communication.

## Timeline (UTC)
- 09:02 Prompt config v23 deployed (reply_draft)
- 09:40 First customer report
- 10:15 Alert fired (JSON validation failures > 2% for 15 min)
- 10:21 Rolled back to v22; error rate normal by 10:24

## Root cause and contributing factors
What happened technically, and WHY the system allowed it
(e.g. the eval set had no cases with multi-currency invoices).

## What went well / what was hard
Detection, containment levers, tooling gaps.

## Action items
| Action | Type (prevent / detect / mitigate) | Owner | Due |
| Add 25 multi-currency cases to the eval set | prevent | … | … |
| Alert on validation failures at 1% for 10 min | detect | … | … |

## The eval or test that would have caught this
Link to the new regression case(s).
```

The last section is specific to AI work: **every incident should leave behind at least one new eval case or attack test** (Modules 5 and 8). That's how your test suite comes to reflect production reality.

<ThinkFirst question="Write the runbook outline (five steps) for one alert: 'Canary token detected in model output'.">

1. **Meaning and impact:** someone extracted (part of) a system prompt. The prompt should contain no secrets, but internal rules are now visible, and the same conversation may be probing for more.
2. **Look first:** the conversation's full trace (inputs, tool calls), the user and tenant, and any other recent conversations from the same user or IP. Saved query: "canary hits in the last 7 days".
3. **Contain:** if it's a single curious user, rate-limit or block that account per policy. If there's a pattern (several accounts, automated), enable the stricter input classifier, and consider disabling tools for that tenant.
4. **Involve:** security on-call (always for canary hits); the account team if a business customer's users are involved.
5. **Recover and learn:** rotate the canary (it's now known), review the prompt for anything sensitive, add the attack to the red-team regression suite (Module 8), and verify the output guard stopped the stream.

</ThinkFirst>

## 🧪 Module 9 lab: operate Relay

**Acceptance criteria:**

1. **Tracing:** every model call, tool call, retrieval and agent run is an OTel span with GenAI attributes, plus tenant, feature and AI config version. One user request is one trace tree across services. Content capture is off by default, and redacted when on.
2. **A tracing backend** (Langfuse, Phoenix or your observability stack) receiving Relay's traces via OTLP.
3. **Versioned AI configs** for every feature, recorded in traces, with a flag-based percentage rollout and a one-switch rollback (demonstrated).
4. **A gateway** for all model calls: keys, per-tenant budgets with atomic reservation, retries in exactly one layer, a circuit breaker and a same-model fallback route, with tests.
5. **Dashboards** for latency (with TTFT), errors and fallback rate, cost per conversation and per tenant, online quality, and safety signals, all sliceable by tenant and config version.
6. **One SLO** with a multi-window burn-rate alert, plus tickets (not pages) for cost and quality drift.
7. **Runbooks** for at least four alerts, a per-feature kill switch, tool revocation, and saved blast-radius queries.
8. **A game day:** simulate a provider outage and a quality regression (deploy a deliberately worse config to a canary). Write a blameless post-mortem for each, using the template above.

<Practice title="Build it yourself: Module 9 wrap-up">

- **Warm-up:** add a per-feature kill switch to Relay, behind a feature flag, with a friendly fallback message. Test that flipping it needs no deploy.
- **Stretch:** write runbooks for the four alerts you're most likely to receive, each with saved trace queries.
- **Boss level:** complete the Module 9 lab, including the game day. A real post-mortem from a simulated incident is a strong portfolio piece: it shows you think about running systems, not just building them.

</Practice>
