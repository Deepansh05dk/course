<Incident title="The provider outage that took down checkout" severity="SEV1">
An e-commerce company added an "AI product Q&A" widget to its product pages. The model provider had a 40-minute partial outage. The widget's API calls hung for 10 minutes each (default timeout), exhausting the web server's worker pool, and **checkout went down with it**. The AI feature wasn't even on the checkout page. It just shared the same servers.
</Incident>

The lesson: an LLM call is a **network dependency with seconds of latency, real failure rates, and per-call cost**. Production architecture exists to contain that. This is the system you'll build piece by piece as Relay.

## Each component: why it exists and what breaks without it

| Component | Why it exists | What breaks without it | Module |
|---|---|---|---|
| **Client UI** | Hides latency (streaming), shows evidence (citations), collects feedback | Users stare at spinners, over-trust wrong answers, and you have no signal | 2 |
| **App API** | Owns auth, sessions, timeouts, and isolates the model from the rest of your system | The checkout incident above | 1 |
| **Input guardrails** | Removes PII, catches injection attempts, enforces policy *before* tokens are spent | Data leaks to third parties; prompt injection reaches tools | 8 |
| **Cache** | Re-uses work: provider prompt caching for stable prefixes, semantic caching for repeated questions | You pay full price for the same 10K-token system prompt millions of times | 10 |
| **Model router** | Sends easy tasks to cheap models and hard ones to strong models | Either overpaying everywhere or failing on hard cases | 1, 10 |
| **Context assembly** | Decides what the model sees: retrieved docs, memory, tool outputs | Hallucinations (missing facts) or confusion and cost (too many facts) | 1, 3–4 |
| **Agent / workflow engine** | Runs multi-step work: tool calls, loops, approvals, budgets | Infinite loops, runaway cost, irreversible actions without a human | 6 |
| **AI gateway** | One place for provider keys, rate limits, retries, fallbacks, spend caps | A provider outage becomes *your* outage; keys scattered across services | 9, 11 |
| **Output validation** | Checks schema, grounding and policy before the user sees it | Broken JSON crashes the app; invented facts reach customers | 1, 8 |
| **Observability** | Traces every call with inputs, outputs, tokens, cost, latency | "Who else got this answer?" has no answer | 9 |
| **Evals** | Measures quality offline (CI) and online (sampled traffic) | Every change is a gamble; regressions found by customers | 5 |

## You don't build it all on day 1

Production maturity is a ladder. Climbing it in the right order is a core FDE skill: customers need value *soon*, but not at the cost of a SEV1.

| Stage | Must have | Can wait |
|---|---|---|
| **Internal prototype** | Timeouts, logging of inputs/outputs, cost tracking | Gateway, router, semantic cache |
| **Pilot with real users** | + Streaming UI, output validation, a small eval set, basic guardrails, spend alerts | Multi-provider fallback, advanced routing |
| **Production** | + Tracing, CI evals, fallbacks, permission-aware retrieval, incident runbook | Fine-tuning, self-hosting |
| **Scale** | + Caching strategy, routing, online evals, cost optimization | Whatever the data says next |

<ThinkFirst question="Relay's first pilot goes to 20 Acme support agents in two weeks. You only have time for three things from the table above. Which three, and why those?">

A strong answer picks the three that prevent the worst outcomes for a **small, internal-but-real** audience:

1. **Logging/tracing of every request** (inputs, outputs, tokens, latency). Without it you can't debug the pilot, measure it, or answer "what happened?" This is the foundation everything else needs.
2. **A small eval set (30–50 real tickets) plus output validation.** It tells you whether the pilot is good enough, and catches regressions as you iterate daily.
3. **Timeouts plus a graceful fallback in a streaming UI.** Agents use it all day, so hanging requests destroy trust fastest.

What can wait: semantic caching (20 users won't hit cost limits), routing, multi-provider fallback. A spend alert is a 5-minute bonus worth adding anyway.

</ThinkFirst>
