## The 10-line prototype trap

This is how almost every AI feature starts:

```python
import anthropic

client = anthropic.Anthropic()

def answer(question: str) -> str:
    msg = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1000,
        messages=[{"role": "user", "content": f"Answer as Acme support: {question}"}],
    )
    return msg.content[-1].text
```

It works in the notebook, and the demo goes great. Now count the production problems hiding in those ten lines:

| Line | What will happen in production |
|---|---|
| `Anthropic()` | Default timeouts are long (minutes). One slow response ties up a web worker, and under load your API stops responding |
| `messages.create` | 429 rate limits and 5xx overloads happen daily at scale. What does the user see? |
| `max_tokens=1000` | Long answers are **silently cut off** mid-sentence (`stop_reason == "max_tokens"`) |
| The prompt | No policy documents, so the model **invents** a plausible policy. That's our incident |
| f-string with `question` | User text is mixed with your instructions, so "ignore previous instructions…" works |
| `content[-1].text` | Assumes the last block is text. Thinking blocks, tool calls and refusals break this |
| No logging | When legal asks "who else got this answer?", you have nothing |
| No eval | You can't tell if tomorrow's prompt tweak made things better or worse |
| No cost tracking | The first bill is a surprise |

None of these are exotic. **Every one of them will happen within weeks of launch.** The rest of this course is about fixing each line properly.

## Deterministic vs stochastic software

| Traditional code | LLM-powered code |
|---|---|
| `add(2, 2)` is always `4` | The same prompt can produce different outputs |
| Bugs reproduce | "It worked when I tried it" is the norm |
| Unit tests with exact asserts | Evals with **rates** ("94% of answers cite a source") |
| Failures are loud (exceptions) | Failures are **silent and fluent** (confidently wrong) |
| Cost is roughly fixed per request | Cost scales with tokens, so a long input or a retry loop gets expensive |
| Latency in milliseconds | Latency in seconds, growing with output length |

Why is it stochastic? A model produces a **probability distribution over the next token**, and the next token is *sampled* from it. Sampling settings like `temperature` and `top_p` shape that randomness. Two things matter for production:

1. **Even "deterministic" settings are not truly deterministic.** Batching, hardware, and provider-side updates mean identical requests can still differ. Never build a system that relies on byte-identical outputs.
2. **These knobs are disappearing on the newest models.** Reasoning models manage their own sampling, and Anthropic's newest API version rejects `temperature`/`top_p`/`top_k` entirely. You control behaviour through **instructions, examples, structured outputs, and validation**, not sampling parameters.

:::tip[The mindset shift]
Stop asking "is my output correct?" and start asking "**what fraction** of outputs are correct, **which kinds** fail, and **what happens** when one does?"
:::

## When NOT to use an LLM

LLMs are the right tool for **ambiguous language**: understanding intent, summarizing, extracting meaning from messy text, and generating drafts. They're the wrong tool when a deterministic solution exists.

<Diagram
	caption="A quick decision filter. Most production systems mix all three: code for the deterministic parts, small models for simple judgments, big models for real ambiguity."
	code={`flowchart TD
    A["New task"] --> B{"Is there an exact, rule-based answer?<br/>math, date parsing, lookups, validation"}
    B -- Yes --> C["Write normal code<br/>fast, free, always correct"]
    B -- No --> D{"Is it a simple, narrow judgment<br/>at very high volume?"}
    D -- Yes --> E["Classic ML or the smallest model<br/>that passes your eval"]
    D -- No --> F{"Does it need open-ended language<br/>understanding or generation?"}
    F -- Yes --> G["LLM, with evals, validation and fallbacks"]
    F -- No --> H["Rethink the task: maybe search,<br/>a form, or a workflow"]`}
/>

Common anti-patterns:

- **Arithmetic and money:** "What's 17% of $2,340.50?" Use code. Have the LLM *call* a calculator tool if it's inside a conversation.
- **Date parsing:** "next Tuesday" → a date. `dateparser` or a few lines of code are free and exact. Let the LLM extract the phrase, and let code resolve it.
- **Exact lookups:** "What's the status of order 8812?" That's a database query. The LLM's job is understanding the question, not remembering the answer.
- **Validation:** emails, phone numbers, schemas. Use regex and Pydantic.
- **Simple classification at huge volume:** sometimes a tiny model, or even a keyword rule, passes your eval at 1/100th of the cost. Measure before assuming you need a frontier model.

<ThinkFirst question="For each task, decide: plain code, small model, or large LLM? (a) Convert '3rd of March next year' into an ISO date. (b) Route 2 million support emails a day into 6 queues. (c) Draft a reply to an angry customer whose shipment was lost, using their order history.">

- **(a) Mostly code.** Date libraries handle this exactly. If the phrase is buried in a long message, an LLM can *extract* it, and code *resolves* it.
- **(b) The smallest thing that passes your eval.** At 2M/day, cost dominates. Try a small model (or a fine-tuned classifier) and compare its accuracy against a large model on a labeled sample. A 1% accuracy gain rarely justifies a 40× cost increase, unless misroutes are very expensive.
- **(c) A large LLM**, with grounding (order history via tools), tone guidance, and probably human review before sending. This is real ambiguity and empathy, which is the LLM's sweet spot.

</ThinkFirst>

<Practice>

- **Warm-up:** take the 10-line prototype above and list, for each line, the exception or failure you'd expect at 10,000 requests a day.
- **Stretch:** run the same prompt 20 times against a model and save the outputs. How many distinct answers did you get? Which differences would matter to a user?
- **Boss level:** build a tiny "LLM or not?" benchmark: 5 tasks (math, dates, lookup, classification, drafting). Solve each with code *and* with an LLM. Record accuracy, latency and cost in a table. You now have real data for every future "should we use an LLM?" debate.

</Practice>
