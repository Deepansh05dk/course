<Incident title="Approve, approve, approve, approve" severity="SEV2">
Relay's first agent version asked for approval on **every** tool call, including read-only lookups. Agents were shown 30 approval prompts a day, each with a raw JSON blob. Within a week they approved everything without reading. Then one approval was a $2,400 refund to the wrong customer, and it sailed through. The approval step existed. **It had stopped working as a control.**
</Incident>

When AI takes actions (refunds, emails, database changes), the human approval step is often your most important safety control. Like any control, it only works if it's **designed to be used well**.

## Decide what needs approval

Not everything should. Classify every action by **reversibility** and **blast radius**:

| Action | Reversible? | Blast radius | Policy |
|---|---|---|---|
| Look up a shipment | Read-only | None | ✅ Auto |
| Draft a reply (not sent) | Yes | None | ✅ Auto, since the human sends it |
| Refund ≤ $100 | Partly | Small | ✅ Auto, with audit log and daily cap |
| Refund > $100 | Partly | Money | 🟡 **Human approval** |
| Email a customer | No | Reputation | 🟡 Human approval (or edit-before-send) |
| Bulk action (> 10 customers) | No | Large | 🔴 Approval by a supervisor, plus a preview of every recipient |
| Delete customer data | No | Legal | ⛔ Not available to the AI at all |

**Principle:** auto-approve what's safe, require approval where it matters, and **don't give the AI tools it should never use**. The safest approval prompt is the one for a tool that doesn't exist.

## Approvals with the AI SDK

AI SDK 7 lets you attach an approval policy per tool with `toolApproval` on `streamText`. The decision can depend on the tool's input:

```ts
// app/api/chat/route.ts (excerpt)
const result = streamText({
	model: anthropic('claude-opus-5-5'),
	instructions:
		'You are Relay, the support assistant for Acme Logistics. ' +
		'Never claim a refund was issued unless the issueRefund tool returned a refundId. ' +
		'If a tool call is denied, do not retry it.',
	messages: await convertToModelMessages(messages),
	tools, // getShipment, issueRefund, ...
	toolApproval: {
		// Small refunds run directly; anything bigger waits for a human.
		issueRefund: ({ amount }) =>
			amount > 100 ? { type: 'user-approval', reason: `Refund of $${amount} needs agent approval` } : undefined,
	},
	stopWhen: isStepCount(5),
	abortSignal: req.signal,
});
```

```ts
// src/ai/tools.ts (excerpt): the side effect carries an idempotency key
issueRefund: tool({
	description: 'Refund a customer for a shipment. Only after checking the refund policy.',
	inputSchema: z.object({
		shipmentId: z.string(),
		amount: z.number().positive().max(5000), // hard upper bound, enforced by the schema
		reason: z.string().describe('One sentence the agent can show the customer'),
	}),
	execute: async ({ shipmentId, amount }, { toolCallId }) =>
		createRefund({ shipmentId, amount, idempotencyKey: `refund:${toolCallId}` }),
}),
```

On the client, the tool part arrives in the `approval-requested` state, and you render an approval card:

```tsx
const { messages, addToolApprovalResponse } = useChat<RelayUIMessage>({
	transport: new DefaultChatTransport({ api: '/api/chat' }),
	// After the agent decides, continue the conversation automatically.
	sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithApprovalResponses,
});

// inside message.parts.map(...)
case 'tool-issueRefund':
	if (part.state === 'approval-requested' && !part.approval.isAutomatic) {
		return (
			<div key={part.toolCallId} className="approval">
				<p>Refund <strong>${part.input.amount}</strong> on {part.input.shipmentId}?</p>
				<p>{part.input.reason}</p>
				<button onClick={() => addToolApprovalResponse({ id: part.approval.id, approved: true })}>Approve</button>
				<button onClick={() => addToolApprovalResponse({ id: part.approval.id, approved: false })}>Deny</button>
			</div>
		);
	}
	if (part.state === 'output-available') return <p key={part.toolCallId}>✅ Refund issued ({part.output.refundId})</p>;
	if (part.state === 'output-denied') return <p key={part.toolCallId}>Refund was not approved.</p>;
	return null;
```

## Making approvals actually work

An approval card is a tiny decision interface. Design it for a **fast, correct decision**:

- **Human-readable summary, not JSON.** "Refund **$340** to **Jane Doe** for **ACM-2025-000183** (glassware broken)."
- **The evidence next to the decision:** the policy excerpt that allows it, the damage photos, the customer's history.
- **Highlight what's unusual:** "⚠️ 3rd refund for this customer this month", "Amount exceeds the shipment value."
- **Edit, don't just approve or deny.** Let the human change the amount or the wording, then approve. Edit-before-send is often better than yes/no.
- **Make denial cheap and informative:** a reason field that feeds back to the model ("Policy requires photos first") and into your eval data.
- **Undo where possible:** emails with a 30-second "unsend" window; refunds with a same-day reversal path.

<ThinkFirst question="Acme wants to automate refunds under $50 with no human involved, to save agent time. What guardrails would you require before agreeing?">

Agreeing is reasonable if the blast radius is bounded and you can see what's happening:

1. **Hard limits outside the model:** schema max ($50), a per-customer daily and monthly cap, a global daily budget, and refunds only for shipments that belong to the requesting customer (checked in code).
2. **Policy checks in code** where possible: delivery date within the refund window, no prior refund on the same shipment.
3. **Idempotency** on every refund, plus reconciliation reports.
4. **Audit and sampling:** every auto-refund is logged with the conversation; a human reviews a random 5% weekly, plus all refunds flagged by anomaly rules (velocity, repeat customers).
5. **Kill switch:** a config flag to instantly route all refunds back to approval.
6. **Eval evidence first:** measured accuracy of the refund decision on historical cases before launch, and the rollout to a small share of traffic first.

That's the autonomy dial from lesson 1: move right only with limits, visibility, and a way back.

</ThinkFirst>
