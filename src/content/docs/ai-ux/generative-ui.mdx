<Incident title="'Your shipment is delayed' — but which one?" severity="SEV3">
Relay's text answers about shipments were correct but hard to use: agents had to read a paragraph to find the ETA, then copy the shipment ID by hand into another system. A two-week experiment replaced the paragraph with a **shipment card** (status chip, location, ETA, a "copy ID" button). Average handling time for tracking tickets dropped by 40 seconds.

**Generative UI** means the model's output is not only text: it can trigger **components**. The mechanism isn't magic. The model calls a tool, the tool returns structured data, and your frontend renders that data with a component *you* designed.

## Define tools once, type them everywhere

```ts
// src/ai/tools.ts
import { tool, type InferUITools, type UIDataTypes, type UIMessage } from 'ai';
import { z } from 'zod';

export const tools = {
	getShipment: tool({
		description: 'Look up the live status of a shipment by its ID (format ACM-YYYY-NNNNNN).',
		inputSchema: z.object({ shipmentId: z.string().regex(/^ACM-\d{4}-\d{6}$/) }),
		execute: async ({ shipmentId }) => lookupShipment(shipmentId), // your backend call
	}),
};

// The UI message type now knows each tool's input and output types.
export type RelayUIMessage = UIMessage<never, UIDataTypes, InferUITools<typeof tools>>;
```

On the server, pass `tools` to `streamText` (and a step limit such as `stopWhen: isStepCount(5)` so the model can call the tool and then write its answer). On the client, each tool call arrives as a typed part named `tool-<name>`, with a **state**:

| `part.state` | Meaning | What to render |
|---|---|---|
| `input-streaming` | The model is still writing the tool arguments | Skeleton / "preparing…" |
| `input-available` | Arguments complete, tool running | Skeleton with the known input ("Looking up ACM-183…") |
| `output-available` | Tool finished | The real component, built from `part.output` |
| `output-error` | Tool failed | A useful error ("Shipment system unavailable, try again") |
| `approval-requested` / `approval-responded` / `output-denied` | Human approval flow | An approval card (lesson 5) |

```tsx
// inside message.parts.map(...)
case 'tool-getShipment':
	switch (part.state) {
		case 'output-available':
			return <ShipmentCard key={part.toolCallId} {...part.output} />;
		case 'output-error':
			return <ErrorChip key={part.toolCallId} text="Couldn't load the shipment. Try again." />;
		default:
			return <ShipmentCardSkeleton key={part.toolCallId} id={part.input?.shipmentId} />;
	}
```

## Designing tool outputs for display

Your tool's return value now has **two audiences**: the model (which reads it to write the answer) and the component (which renders it). Design for both:

- **Return structured, stable fields** (`status: "delayed"`), not pre-formatted prose. The component formats; the model reasons.
- **Return only what's needed.** A 4,000-field database row bloats the model's context (cost, latency) *and* the payload sent to the browser.
- **Never return secrets or internal-only fields.** Tool outputs travel to the client in the stream, so anything in the output is visible in the browser's network tab.
- **Version your components:** old conversations replay old tool outputs. A component must handle older output shapes (or fall back to JSON or text) without crashing.

<FailureCard
	title="Markdown that ran a script"
	symptom="A pen-tester gets the assistant to output a link like `javascript:...` or raw HTML, and the chat renders it."
	cause="Model output was rendered as unsanitized HTML or markdown. Model output is **untrusted input**: it can be steered by prompt injection from documents and tickets."
	detect="Security tests that feed hostile markdown and HTML through the renderer."
	fix="Render with a markdown library configured to strip raw HTML, allow only `http(s)` links, and treat images carefully (Module 8 covers image-based data exfiltration). Never use `dangerouslySetInnerHTML` on model output."
/>

<FailureCard
	title="One unknown part crashes the chat"
	symptom="After adding a new tool on the server, older deployed frontends show a blank screen for some conversations."
	cause="The client's `switch` over part types threw on an unknown part type (or tried to read fields that didn't exist)."
	detect="Error monitoring on the frontend (Sentry, etc.) grouped by part type."
	fix="Always have a safe `default` branch (render nothing or a generic 'tool used' chip), keep frontend and backend tool sets versioned together, and deploy backend changes that add tools only after the UI can handle them."
/>

<ThinkFirst question="Product wants the model to generate arbitrary React/HTML for every answer ('fully generative UI') instead of picking from your component library. What are the risks, and what would you propose instead?">

**Risks of arbitrary model-generated UI:**

- **Security:** generated HTML/JS is an XSS vector, especially when injection-controlled content (tickets, documents) influences the model.
- **Consistency and accessibility:** every answer looks different, breaks your design system, and fails accessibility checks unpredictably.
- **Reliability and cost:** generating markup is many output tokens (slow, expensive) and often invalid.
- **Testability:** you can't snapshot-test or eval UIs that never look the same twice.

**Proposal: a constrained component vocabulary.** Offer the model a catalogue of safe, designed components (cards, tables, charts, timelines, forms) via tools or a schema. The model picks the component and fills in **data**; your code renders it. If they need more flexibility, add a generic `Table` and `Chart` with schema-validated props, and render them inside a sandboxed iframe for anything truly custom. You get 90% of the flexibility with none of the XSS.

</ThinkFirst>
