<Incident title="'What's the fraud-review threshold?'" severity="SEV1">
A support agent asked Relay why a large refund was delayed. The answer quoted an internal finance document, including the exact amount above which refunds trigger manual fraud review. That threshold was confidential, visible only to the finance team in the document system. The RAG index had ingested **all** policies into one pool, with no permissions. Anyone who could ask Relay could read everything Relay could read.
</Incident>

This is the most serious RAG failure mode in enterprise and FDE work. A RAG system is **a new way to read documents**, so it must respect the same access rules as the documents themselves. Getting it wrong is a data breach, not a quality bug.

## The golden rule

> A user must never receive, directly or through a generated answer, content from a document they couldn't open in the source system.

"Through a generated answer" matters: even if you never *show* the chunk, a summary that mentions the confidential number is a leak.

## Architecture

Key decisions:

1. **Copy ACLs at ingestion**, per chunk (`allowed_groups`, `tenant_id`), and keep them in sync when permissions change in the source system.
2. **Resolve the user's groups from your identity system** (SSO / the identity provider), never from anything the user or the LLM writes.
3. **Filter in the data layer, before ranking:** the user's search must only ever see permitted rows.
4. **Fail closed:** if identity context is missing, return nothing.

## Row-level security that fails closed

Postgres **row-level security (RLS)** applies a policy to every query on a table, so a forgotten `WHERE` clause can't leak data. This policy was tested on PostgreSQL 16 while writing this lesson:

```sql
-- Chunks carry the ACL copied from the source system at ingestion.
ALTER TABLE chunks ADD COLUMN allowed_groups text[] NOT NULL DEFAULT '{}';

-- The application connects as a non-owner role. RLS doesn't apply to table owners or superusers.
CREATE ROLE relay_app LOGIN;
GRANT SELECT ON chunks TO relay_app;

ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY chunk_access ON chunks FOR SELECT TO relay_app USING (
    tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::int
    AND allowed_groups && string_to_array(NULLIF(current_setting('app.user_groups', true), ''), ',')
);
```

```python
# app/rag/secure_search.py: identity comes from the authenticated session, never from the prompt
def search_as_user(conn, user, query_vec, query_text: str, k: int = 10) -> list[tuple]:
    with conn.transaction():
        # SET LOCAL scopes the settings to this transaction only
        conn.execute("SELECT set_config('app.tenant_id', %s, true)", (str(user.tenant_id),))
        conn.execute("SELECT set_config('app.user_groups', %s, true)", (",".join(user.groups),))
        return conn.execute(HYBRID_SEARCH_SQL, {"q": query_vec, "text": query_text, "k": k}).fetchall()
```

Behaviour verified against the test data:

| Session context | Rows visible |
|---|---|
| Tenant 1, groups `support` | Support documents only (finance-only document hidden) |
| Tenant 1, groups `support,finance` | Support and finance documents |
| No context set at all | **0 rows** (fails closed) |
| Tenant 2, any groups | Tenant 2's documents only, never tenant 1's |

The `NULLIF(current_setting(..., true), '')` pattern matters: without it, a missing setting raises an error in some cases and an empty string in others. With it, missing context always means **no rows**.

## The leakage paths people forget

| Path | How it leaks | Defence |
|---|---|---|
| **Response caches** | A cached answer generated for a finance user is served to a support agent | Include the permission scope in the cache key, or don't cache permissioned answers |
| **Semantic caches** (Module 10) | A "similar question" returns another user's answer | Partition caches per permission set |
| **Conversation memory / summaries** | A summary stored at the session level carries restricted facts into later turns | Treat memory as derived data with the strictest permission of its inputs |
| **Precomputed summaries / reports** | Summaries built over all documents mix permission levels | Build them per permission scope |
| **Traces and logs** | Retrieved restricted chunks are visible to everyone with access to the observability tool | Access control and redaction in tracing (Module 9) |
| **Stale ACLs** | Someone's access was revoked in the source system but not in the index | ACL change events plus a nightly re-sync; alert on sync lag |

<ThinkFirst question="An FDE engagement: the customer's documents live in SharePoint with complex nested permissions (user → groups → nested groups, plus per-document sharing links). Security requires that the assistant 'never shows anything a user can't open in SharePoint'. How do you design and prove this?">

**Design:**

1. **Ingest ACLs, flattened:** for each document, resolve which principals (users and groups) can read it, store them per chunk, and re-sync on permission change events plus a nightly reconciliation.
2. **Resolve the user's effective groups at query time** from the identity provider (including nested groups), cached briefly.
3. **Enforce in the data layer** (RLS or a mandatory filter in the search service) before ranking. Fail closed.
4. **Sharing links and edge cases:** for anything you can't model reliably (anonymous links, external sharing), exclude those documents from the index until you can. Prefer under-retrieval to leakage.
5. **Optional belt-and-braces:** a post-retrieval check against the source system's permission API for the final top chunks (slower, but a strong guarantee for highly sensitive content).

**Prove it:**

- An automated **permission test suite**: test users with known memberships, canary documents with unique phrases ("canary-7731"), and assertions that unauthorised users never see the phrase in retrieved chunks *or* answers.
- Red-team prompts that try to talk past restrictions.
- Audit logs of which chunks each user retrieved, so the customer's security team can verify.

</ThinkFirst>

<Practice>

- **Warm-up:** add `allowed_groups` to your chunk table, write the RLS policy above, and test it with two roles.
- **Stretch:** write a pytest suite with three test users and canary documents. Assert that no user ever retrieves a canary chunk they shouldn't, including when the query is the canary phrase itself.
- **Boss level:** add the **leakage-path checklist** to Relay: permission-scoped cache keys, permission-tagged conversation memory, and trace redaction. Write one test per path.

</Practice>
