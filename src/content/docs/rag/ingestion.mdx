<Incident title="The refund policy that was deleted, but not really" severity="SEV1">
Acme withdrew its "90-day goodwill refund" promotion and deleted the PDF from the policy drive. Three weeks later, Relay was still citing it to customers. The ingestion job only ever **added and updated** documents. It never noticed that one had disappeared. The vector index kept the old chunks forever.
</Incident>

Most RAG quality problems are born in ingestion. The model can only be as right as the text you feed it, and production ingestion has to cope with messy formats, constant change, and deletions.

## Parsing: getting clean text out of real documents

| Source | Typical problems | Approaches |
|---|---|---|
| **Digital PDFs** | Multi-column layouts, headers and footers on every page, hyphenation, reading order | Layout-aware PDF parsers (PyMuPDF, pdfplumber); document-AI libraries (Docling, Unstructured) |
| **Tables** | Flattened into word soup, losing which value belongs to which column | Table-aware extraction to markdown or HTML; keep each table as one unit |
| **Scans / images** | No text layer at all | OCR, or a **vision-capable LLM** that reads the page and returns markdown |
| **HTML / wikis** | Navigation, cookie banners, boilerplate | Extract the main content; keep heading structure |
| **Office docs, email** | Embedded attachments, quoted reply chains | Format-specific parsers; strip quoted history; recurse into attachments |

:::tip[Look at your parsed text]
The single highest-value ingestion habit: **print the parsed output of 20 random documents and read it.** Broken tables, missing pages and garbled reading order are obvious to a human in seconds, and invisible in a retrieval score.
:::

## Metadata: the information you'll wish you had

Store with every chunk (not just the text):

| Field | Why |
|---|---|
| `doc_id`, `source_uri`, `title` | Citations and debugging |
| `section` / heading path | Context for the chunk (lesson 3), and better citations |
| `page` | "See page 4" citations for PDFs |
| `version`, `effective_date`, `updated_at` | Resolving conflicts between old and new versions (lesson 6) |
| `content_hash` | Incremental sync (below) |
| `language` | Language-aware search and answers |
| `allowed_groups`, `tenant_id` | Permission-aware retrieval (lesson 7) |
| `embedding_model` | The index contract (Module 3) |

## Incremental sync: re-embed only what changed

Re-embedding everything every night is slow and expensive, and it hides problems. Instead, hash each document's content and compare with what's indexed:

```python
# app/rag/ingest.py: only re-embed what changed
import hashlib


def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def plan_sync(source_docs: dict[str, str], indexed_hashes: dict[str, str]) -> dict[str, list[str]]:
    """source_docs: doc_id -> current text. indexed_hashes: doc_id -> hash stored at last ingestion."""
    current = {doc_id: content_hash(text) for doc_id, text in source_docs.items()}
    return {
        "add": [d for d in current if d not in indexed_hashes],
        "update": [d for d in current if d in indexed_hashes and current[d] != indexed_hashes[d]],
        "delete": [d for d in indexed_hashes if d not in current],  # removed at the source: must leave the index
        "unchanged": [d for d in current if indexed_hashes.get(d) == current[d]],
    }
```

For an update, **replace all of the document's chunks in one transaction** (delete the old ones, insert the new ones), so search never sees half-old, half-new content. The `delete` list is the line that would have prevented the incident above.

## Freshness as a metric

**Freshness lag** = time between a change in the source and that change being searchable. Decide the target with the business ("policy changes must be live within 1 hour"), then monitor it. Webhooks from the source system beat nightly batch jobs when freshness matters.

<ThinkFirst question="Acme's 200 policy PDFs live in a shared drive. About 15 change per month, mostly small edits, and 30 are scanned images. Design the ingestion pipeline: triggers, parsing, quality checks, and how a policy update reaches Relay safely.">

1. **Trigger:** drive change notifications (webhook) plus a nightly reconciliation job that lists the whole drive (catches missed events **and deletions**).
2. **Parse:** a layout-aware parser for digital PDFs, with tables extracted as markdown. Pages with little or no text go to OCR or a vision model.
3. **Quality gate:** minimum text per page, table detection sanity, no duplicate-header noise, and a diff summary ("section 4.2 changed: 30 → 14 days"). Failures are quarantined, and the **previous version stays live**.
4. **Chunk + metadata:** section path, page, `effective_date`, version, permissions, content hash.
5. **Atomic swap per document:** delete the old chunks and insert the new ones in one transaction.
6. **Post-ingestion checks:** run the retrieval eval subset for the changed documents ("What is the refund window?" must retrieve the new section) before announcing the update.
7. **Metrics:** freshness lag, parse failure rate, chunks per document over time.

For high-stakes changes (refund terms), a human in the policy team can approve the diff before it goes live. That's cheap insurance.

</ThinkFirst>
