<Incident title="The question that needed three documents" severity="SEV3">
"Customer ACM-C-2201 shipped insured glassware to Norway and it arrived broken. What can we offer?" Relay's single-shot RAG retrieved the damage policy and nothing else. The real answer needed the customer's contract tier (from the CRM), the insurance rules, the fragile-goods cap, **and** the Norway customs note about returns. Classic RAG is a fixed pipeline: one query, one retrieval, one answer. **Agentic RAG** gives the model retrieval as a **tool**: it can search, read, decide what's missing, and search again, combining documents with live data along the way.

## Retrieval as a tool

The search tool is just your hybrid search plus reranker with a good description:

```python
SEARCH_TOOL = {
    "name": "search_policies",
    "description": (
        "Search Acme's policy documents (refunds, damage, insurance, customs). "
        "Returns up to 5 passages with document title, section and effective date. "
        "Use specific queries; search again with different terms if results are not relevant. "
        "Do not use this for live shipment or customer data."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "A specific search query, not the user's whole message"},
        },
        "required": ["query"],
    },
}
```

You'll build the full tool-calling loop in Module 6. The RAG-specific design points are:

- **Return compact, cited results:** title, section, effective date, and the passage. Not whole documents.
- **Budget the loop:** a maximum number of searches (e.g. 5) and a token budget. Agents happily search forever.
- **Permission-aware, always:** the tool executes **as the user** (lesson 7). The agent can't search what the user can't see.

## When is agentic RAG worth it?

| Use single-shot RAG when… | Use agentic RAG when… |
|---|---|
| Most questions are answered by one passage | Questions need several sources, or combine docs with live data |
| Latency budget is tight (chat, autocomplete) | Users accept a few extra seconds for a much better answer |
| Volume is high and cost matters | Stakes per answer are high (claims, compliance, research) |
| You want a predictable, testable pipeline | You have evals that measure trajectories (Module 5) |

A common production pattern is **routing**: single-shot by default, agentic for questions a classifier flags as complex, or when single-shot retrieval quality is low.

## 🧪 Module 4 lab: Relay policy Q&A

Build it in `relay`, using the ingestion from this module and the pgvector store from Module 3. **Acceptance criteria:**

1. **Ingestion** of at least 50 realistic policy documents (generate them, or use public policy PDFs), with tables and some scans: parsing, quality gate, structure-aware chunking with prepended context, content-hash sync **with deletions**, and permissions copied per chunk.
2. **Hybrid search** (vector + full-text with RRF) and a **reranker**.
3. **Conversational query rewriting** for follow-ups, preserving identifiers.
4. **Grounded answers with native citations**, a "not covered" gate tuned on unanswerable questions, and the number/date verification check.
5. **Row-level security** with a permission test suite using canary documents.
6. **A retrieval eval** with at least 40 labelled questions (including 10 unanswerable and 5 multi-hop): recall@5 and MRR for keyword, semantic, hybrid, and hybrid with reranking, in a table.
7. **The UI** from Module 2 showing citation chips, conflict banners, and the "not covered" state.
8. `docs/module-4.md`: your ablation table, the chosen configuration with justification, and **the three worst failures you found** with their root causes.

<ThinkFirst question="Your Module 4 eval: recall@5 = 0.88, but users still report wrong answers in about 10% of cases. Name three different root causes that could explain the gap between good retrieval and bad answers, and how you'd tell them apart.">

1. **Generation isn't faithful:** the right chunk is in context, but the answer contradicts or paraphrases it wrongly. *Tell:* run a faithfulness check on the failing cases. If the answer isn't supported by the retrieved text, it's generation.
2. **The eval set doesn't match real traffic:** your 40 questions are easier, or differently distributed, than what users ask. *Tell:* sample 50 real production questions and label them; compare recall on real versus eval questions.
3. **Right topic, wrong version:** retrieval found a relevant chunk, but a superseded or conflicting one. *Tell:* check the cited documents' effective dates in the failing cases.

Bonus causes: questions that need several hops (single-shot can't answer them), "correct but useless" answers that users mark wrong, and permission filtering hiding the needed document for that user.

That's exactly the skill Module 5 builds: **error analysis on real traces to find out which stage fails, before fixing anything.**

</ThinkFirst>
