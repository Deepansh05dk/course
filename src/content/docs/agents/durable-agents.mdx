<Incident title="The deploy that refunded twice" severity="SEV1">
Relay's refund agent ran inside the web server process. A deploy restarted the servers while 14 refund tasks were mid-flight. The retry logic restarted those tasks **from the beginning**. Six of them had already issued the refund before the restart, and issued it again after. The payments API had no idempotency key. Total double-payments: 2,340 EUR, discovered by finance a week later.
</Incident>

A chat answer that fails can simply be retried. An agent that **takes actions over minutes, hours or days** (waiting for a human approval on Friday that comes on Monday) needs to survive crashes, deploys and restarts **without repeating its side effects**. That's **durable execution**.

## The core ideas

| Idea | What it means | Relay example |
|---|---|---|
| **Checkpointing** | Save the agent's state after every step, in a database | After "assess" and after "approve", state is persisted |
| **Resume, don't restart** | After a crash, continue from the last checkpoint | The refund task resumes at "issue_refund", not at "assess" |
| **Idempotent side effects** | Repeating a step can't repeat its effect | The payments API dedupes on an idempotency key |
| **Durable waits** | Waiting for a human doesn't hold a process or a thread | The approval can take 3 days; nothing is running meanwhile |
| **Exactly-once illusion** | "At least once" execution + idempotency = effectively once | Retries are safe by construction |

## Where idempotency keys come from

The key must identify **the logical action**, and be identical every time that action is retried, **in any process**:

- ✅ `refund:{ticket_id}:{shipment_id}:{amount}`, or an ID generated once and saved in the checkpoint **before** the call.
- ❌ A random UUID generated inside the retried step: every retry gets a new key, so no deduplication.
- ❌ Python's built-in `hash()` of a string: it's **randomized per process**, so after a restart the same action gets a different key. (This exact bug was caught while testing this lesson's example. Use `hashlib`.)

## Tools for durable execution

| Option | Model | Good for |
|---|---|---|
| **LangGraph checkpointers** (SQLite, Postgres) | State saved after each graph step; `interrupt` for human input | Agent workflows in Python (next lesson) |
| **Temporal** (and similar workflow engines) | Workflows as code; every step's result recorded in an event history and replayed after crashes | Long-running, business-critical processes with many external calls |
| **A job queue + database state** | You checkpoint manually; workers pick up resumable tasks | Simple flows where you want full control |
| **Managed agent platforms** | The provider hosts the loop and session state | Hosted agents where that fits your data and control requirements |

## Human approval in backend agents

In [Module 2](/ai-ux/human-in-the-loop/) you designed approval **UX**. In the backend, an approval is a **durable pause**:

1. The agent reaches a gated action and records a pending approval (what, why, evidence) in the database.
2. The task **stops**, with no thread blocked, no open connection.
3. The approval UI shows the request; a human approves, edits or denies it, and the decision is stored with who and when.
4. The decision **resumes** the task from its checkpoint, with the decision as input.
5. Approvals **expire**: an unanswered approval after N days escalates or cancels, so nothing silently executes months later.

<ThinkFirst question="An approval for a 2,000 EUR refund has been pending for 9 days. What should the system do, and how should that behaviour be designed up front?">

Design approvals as **records with a lifecycle**, not open-ended waits:

1. **Expiry policy, decided up front:** for example, a reminder after 24 hours, escalation to a supervisor after 3 days, and auto-cancel with notification after 7 days. A 9-day-old approval should already have been handled.
2. **Re-validation on approval:** even if someone approves on day 9, re-check the preconditions (claim still open, amount unchanged, customer still eligible) before executing.
3. **Customer communication:** the customer shouldn't wait silently. The agent can send a "still under review" update, as an idempotent, durable step.
4. **Monitoring:** a dashboard of pending approvals by age, and an alert on any older than the policy allows.

</ThinkFirst>
