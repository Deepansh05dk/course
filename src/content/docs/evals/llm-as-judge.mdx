<Incident title="The judge that loved long answers" severity="SEV3">
Relay's team used an LLM judge with the prompt "Rate this answer's quality from 1 to 10." A prompt change made answers 40% longer, with more caveats and repetition. The judge's average rose from 7.1 to 8.3, and the change shipped. Agents hated it: the drafts took longer to edit. The judge had been rewarding **length**, not quality.
</Incident>

Once error analysis tells you *what* to measure, you need **scorers**: functions that look at an output and return pass or fail. Always try code first; use LLM judges for the rest.

## Code-based checks

These are cheap, fast, deterministic, and never drift. They cover more than people expect:

```python
# evals/checks.py
import re

PROMISE = re.compile(r"\b(we will|we'll|you will receive|approved?)\b.*\brefund", re.I)
ORDER_ID = re.compile(r"ACM-\d{4}-\d{6}")
NUMBER = re.compile(r"\d+(?:[.,]\d+)?")


def no_refund_promise(output: str) -> bool:
    return not PROMISE.search(output)


def does_not_ask_for_known_id(ticket: str, output: str) -> bool:
    """The #1 failure from error analysis: asking for an order number already provided."""
    asks = re.search(r"(share|provide|send).{0,30}(order|shipment) (number|id)", output, re.I)
    return not (ORDER_ID.search(ticket) and asks)


def numbers_are_grounded(output: str, sources: list[str]) -> bool:
    """Every number in the answer must appear in at least one source passage."""
    source_text = " ".join(sources)
    return all(n in source_text for n in NUMBER.findall(output))


def cited_ids_were_retrieved(cited: list[str], retrieved: list[str]) -> bool:
    return set(cited) <= set(retrieved)
```

Each one maps directly to a failure category from your taxonomy. The table in the [error analysis lesson](/evals/error-analysis/) shows the pattern: **every category gets its own check.**

## When you need a judge

Some criteria need judgment: "Does the answer address what the customer actually asked?", "Is it faithful to the sources?", "Is the tone right for an angry customer?". An **LLM judge** is a model call that grades an output against a rubric.

## Designing a judge that works

| Do | Don't |
|---|---|
| **One criterion per judge** ("faithful to sources") | One judge that rates "overall quality" |
| **Binary pass/fail** with an explicit rule | 1–10 scales (inconsistent, and they reward length) |
| **Critique before verdict**, so the judge reasons first | Ask for the score alone |
| Include **pass and fail examples** from your labelled data (lesson 2) | Leave "good" undefined |
| Give the judge **the context** it needs (sources, the policy) | Ask it to judge facts it can't see |
| **Calibrate against human labels** (next lesson) | Trust it because it sounds smart |

```python
# evals/judges.py
import anthropic
from pydantic import BaseModel, Field

client = anthropic.Anthropic()

FAITHFULNESS_RUBRIC = """You are evaluating whether a support reply is FAITHFUL to the provided policy excerpts.

PASS if every factual claim in the reply (deadlines, amounts, conditions, requirements) is directly supported by the excerpts.
FAIL if the reply states any fact, number or condition that the excerpts do not support, or contradicts them.
Ignore tone, length and style. Only judge factual support.

Example FAIL: excerpts say "change the address until the parcel leaves the warehouse"; reply adds "for a 5 EUR fee".
Example PASS: excerpts say "refunds within 30 days, not for perishables"; reply says "you can get a refund within 30 days unless the item is perishable"."""


class Verdict(BaseModel):
    critique: str = Field(description="Two or three sentences: which claims are or are not supported, and why")
    passed: bool


def judge_faithfulness(reply: str, excerpts: list[str]) -> Verdict:
    response = client.messages.parse(
        model="claude-sonnet-5-5",
        max_tokens=4000,
        system=FAITHFULNESS_RUBRIC,
        messages=[{
            "role": "user",
            "content": "<excerpts>\n" + "\n---\n".join(excerpts) + "\n</excerpts>\n\n<reply>\n" + reply + "\n</reply>",
        }],
        output_format=Verdict,  # critique comes first in the schema, so reasoning precedes the verdict
    )
    return response.parsed_output
```

## Known judge biases

| Bias | What happens | Mitigation |
|---|---|---|
| **Verbosity bias** | Longer answers judged better | Binary criteria that ignore length; pair with a length check |
| **Position bias** | In A-vs-B comparisons, the first (or second) option is favoured | Run both orders and require agreement |
| **Self-preference** | A judge favours outputs from its own model family | Use a different model family as judge, or calibrate carefully |
| **Leniency** | Judges tend to pass borderline cases | Include hard fail examples; measure TNR (next lesson) |
| **Rubric drift** | A changed judge prompt silently changes every historical score | Version judge prompts; re-calibrate after any change |

**Rubric (one criterion: empathetic acknowledgement):**

> PASS if the reply, before any policy details, (1) acknowledges the customer's frustration specifically (not a generic "sorry for any inconvenience") and (2) takes ownership with a concrete next step. FAIL if it opens with policy, blames the customer, is sarcastic or defensive, or uses only a generic apology.

**Examples:**

- PASS: "I'm really sorry: two lost parcels in a month is not acceptable. I've opened a claim for ACM-…, and you'll hear from us by tomorrow."
- FAIL: "Per policy, packages without updates for 14 days are treated as lost." (no acknowledgement)
- FAIL: "We apologize for any inconvenience caused." (generic)

**Exclude deliberately:** factual correctness, length, and grammar. Those belong to other checks. Mixing them in makes the verdict unactionable and introduces verbosity bias.

Then label 50 real angry-customer replies yourself, and calibrate (next lesson).

</ThinkFirst>
