<Incident title="91% accurate, and useless" severity="SEV2">
The team validated their faithfulness judge: it agreed with human labels 91% of the time. They trusted it. Then an audit found that it caught only **3 of 20** real hallucinations. The validation set was 90% passing answers, so a judge that said "pass" to almost everything still scored 91% accuracy. **Accuracy hid the only thing that mattered: catching failures.**
</Incident>

An LLM judge is a model, and models make mistakes. Before you trust a number produced by a judge, measure the judge itself against human labels, the same way you'd validate any classifier.

## The four outcomes

On a set of outputs labelled by humans (lesson 2), compare the judge's verdicts:

| | Judge says **pass** | Judge says **fail** |
|---|---|---|
| **Human says pass** | True positive (TP) | False negative (FN): judge is too strict |
| **Human says fail** | False positive (FP): **judge misses a real failure** | True negative (TN) |

Two numbers matter, and they must be reported **separately**:

- **TPR (true positive rate)** = TP / (TP + FN): of the truly good outputs, how many does the judge pass?
- **TNR (true negative rate)** = TN / (TN + FP): of the truly bad outputs, how many does the judge **catch**?

In the incident: high accuracy, high TPR, and a TNR of 3/20 = 15%. For a judge whose job is catching hallucinations, TNR is the number that matters.

## The calibration loop

1. **Label a balanced set:** you need enough **failures** to measure TNR. If failures are rare, sample them deliberately (thumbs-down, error analysis finds). Aim for dozens of each class, not 3.
2. **Split** into dev and test.
3. **Iterate on dev:** run the judge, read every disagreement, fix the rubric (clearer rules, better examples), and repeat.
4. **Measure once on test** and report TPR and TNR.
5. **Re-calibrate** whenever the judge prompt, judge model, or the system being judged changes significantly.

```python
# evals/judge_calibration.py
def judge_agreement(human: list[bool], judge: list[bool]) -> dict:
    """Compare an LLM judge's pass/fail labels with human labels on the same cases."""
    tp = sum(h and j for h, j in zip(human, judge))           # both say pass
    tn = sum(not h and not j for h, j in zip(human, judge))   # both say fail
    fp = sum(not h and j for h, j in zip(human, judge))       # judge passes a real failure
    fn = sum(h and not j for h, j in zip(human, judge))       # judge fails a real pass
    return {
        "tpr": tp / (tp + fn) if tp + fn else float("nan"),   # passes recognised
        "tnr": tn / (tn + fp) if tn + fp else float("nan"),   # failures caught
        "accuracy": (tp + tn) / len(human),
        "confusion": {"tp": tp, "tn": tn, "fp": fp, "fn": fn},
    }
```

## Correcting the pass rate you report

Even a well-calibrated judge makes mistakes, so its raw pass rate on new traffic is biased. If you know its TPR and TNR, you can estimate the **true** pass rate:

> true pass rate ≈ (observed pass rate + TNR − 1) / (TPR + TNR − 1)

```python
def corrected_pass_rate(observed: float, tpr: float, tnr: float) -> float:
    """Estimate the true pass rate from the judge's observed rate and its measured error rates."""
    denom = tpr + tnr - 1
    if denom <= 0:
        raise ValueError("judge is no better than chance; fix the judge before trusting any rate")
    return min(1.0, max(0.0, (observed + tnr - 1) / denom))
```

For example, with TPR = 0.95 and TNR = 0.75, a judge reporting an 81% pass rate implies a true pass rate of about 80%. (Both functions are unit-tested with exactly these numbers.) Play with it:

<ThinkFirst question="Your hallucination judge on the test split: TPR = 0.97, TNR = 0.60. Product wants to use it as a CI gate that blocks releases if faithfulness drops. Is it ready? What would you do?">

**Not ready as a gate.** A TNR of 0.60 means it **misses 40% of real hallucinations**. A release could double the hallucination rate and the gate would still often pass. (The high TPR only means it rarely flags good answers.)

**What to do:**

1. **Read the false positives** (hallucinations the judge passed). What do they have in common? Often subtle numeric changes, added conditions, or claims that sound generic.
2. **Improve the judge:** a sharper rubric ("any number, deadline or condition not in the excerpts is a FAIL"), fail examples of exactly those types, and claim-by-claim checking (list the claims, then check each).
3. **Offload what code can do:** the deterministic number/date grounding check catches a large class of hallucinations with perfect consistency. Combine it with the judge.
4. **Re-measure on test.** Only gate on it once the TNR is high enough for the risk (and say what "enough" means in writing).
5. Meanwhile, use it as a **monitor** (trend lines, sampled human review), not a gate.

</ThinkFirst>
