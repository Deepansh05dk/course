<Incident title="The metrics dashboard nobody looked behind" severity="SEV3">
A team installed an eval framework and turned on its ten default metrics: "helpfulness", "coherence", "toxicity", and others. Scores were all 0.8–0.9. Meanwhile, the actual top problem, found later by reading 100 conversations in an afternoon, was that the assistant **asked customers for their order number even when they'd already given it**. None of the generic metrics could see that.
</Incident>

The most valuable eval activity isn't writing scorers. It's **looking at your data**. Generic metrics measure generic things; your product fails in specific ways that you only discover by reading traces.

## The process

<Diagram
	caption="Error analysis in four steps. A first pass on 100 traces takes a few hours and usually reveals the top problems."
	code={`flowchart LR
    A["1. Sample traces<br/>~100, diverse and recent"] --> B["2. Open coding<br/>write a free-text note on<br/>what went wrong in each"]
    B --> C["3. Axial coding<br/>group notes into a<br/>failure taxonomy"]
    C --> D["4. Count and prioritise<br/>frequency x severity"]
    D --> E["Write evals for the top failures<br/>and fix them"]`}
/>

1. **Sample:** pull about 100 traces (inputs, retrieved context, tool calls, outputs). Mix random samples with known-bad ones (thumbs-down, big edits, escalations), and cover different segments (languages, ticket types).
2. **Open coding:** for each trace, write one short note about the **first** thing that went wrong, in your own words ("asked for the order number again", "quoted the old refund window"). No predefined categories yet: you're discovering them.
3. **Axial coding:** group similar notes into categories: your **failure taxonomy**. Typically 5–10 categories emerge.
4. **Count and prioritise:** how often does each category occur, and how bad is it? Fix the top of the list first.

:::tip[Who should do this?]
Someone who knows what "good" looks like in this domain. For Relay, a senior support agent or policy expert, together with the engineer. FDEs often run this session **with the customer's experts**, and it builds enormous trust: they see you taking their judgment seriously.
:::

These 8 traces are a slice of a 100-trace review. Across all 100, the most common failure was **ignored context** (asking for information the customer already gave), as the table below shows. No generic "helpfulness" metric would have named it. That's the point of error analysis.

## Pass/fail beats 1–10 scales

Label each trace **pass or fail** against a clear rule, not "quality: 7/10". Binary labels:

- **force a decision** about what's acceptable (the rule gets written down);
- are **more consistent** across reviewers (is a 6 different from a 7?);
- **map directly to actions** (fix the fails);
- make **judges easier to calibrate** (lesson 5).

Capture nuance in the free-text note and the failure category, not in the score.

## Turning the taxonomy into action

| Failure category | Count (of 100) | Severity | Fix | Eval |
|---|---|---|---|---|
| Ignored context (asks for info already given) | 14 | Medium | Prompt rule plus extracting entities into case state | Code check: if the ticket contains an order ID, the reply must not ask for it |
| Unsafe promise (refunds) | 6 | **High** | Prompt rule plus approval flow (Module 2) | Regex check plus LLM judge; **critical**: must be 0 |
| Missed retrieval | 9 | High | Hybrid plus reranker (Module 4) | Retrieval recall@5 on these questions |
| Hallucinated policy detail | 5 | High | Grounding prompt, number/date verification | Code check: numbers in the answer appear in sources |
| Wrong tone with angry customers | 8 | Low–medium | Tone guidance plus few-shot examples | LLM judge with a rubric |

Each row becomes **eval cases plus a scorer**, and each fix is proven against them.

<ThinkFirst question="You and a colleague labelled the same 50 traces and agreed on pass/fail only 70% of the time. What does that tell you, and what do you do before labelling more?">

**It tells you the definition of "pass" is ambiguous, not that one of you is wrong.** Seventy percent agreement means any metric built on these labels (including an LLM judge calibrated against them) is shaky.

**Before labelling more:**

1. **Review the disagreements together.** For each one, decide the right label *and why*.
2. **Write the rule down** as explicit pass criteria. For example: "A reply passes if it answers the customer's actual question using only policy facts, includes required conditions, and makes no unapproved promises. Missing non-requested extras (e.g. battery rules when batteries aren't mentioned) is not a failure."
3. **Re-label a fresh sample** independently and measure agreement again. Aim for high agreement (often 85–90%+) on clear criteria.
4. Keep tricky examples as **anchor cases** in your labelling guide.

That written rule becomes the rubric for your LLM judge in lesson 4.

</ThinkFirst>

<Practice>

- **Warm-up:** do the labelling exercise above, then write the one-sentence pass rule that would have resolved trace t8.
- **Stretch:** pull 50 traces from your own Relay logs (or generate realistic ones), do open coding in a spreadsheet, and build your taxonomy with counts.
- **Boss level:** build a tiny **trace review app** in your Relay UI (your frontend strength again): one trace per screen, keyboard shortcuts for pass/fail, a note field, category tags, and an export to JSONL. Teams that make reviewing fast review more, and their products get better.

</Practice>
