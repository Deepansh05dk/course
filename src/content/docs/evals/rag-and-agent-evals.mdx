<Incident title="The agent that passed by accident" severity="SEV2">
Relay's refund agent passed 95% of its end-to-end eval: the final reply was correct. Then a trace review found that in 20% of "passing" cases the agent had called `issueRefund` **twice** (the second call failed on the idempotency key), or looked up the **wrong customer** before correcting itself. Outcome-only scoring had hidden risky behaviour that would eventually cause a real incident.
</Incident>

RAG systems and agents are pipelines. A single end-to-end score tells you **that** something is wrong, not **where**. This lesson is about measuring each stage, so every failure points at its fix.

## The RAG triad

<Diagram
	caption="Three relationships, three questions. Each failure mode has a different fix."
	code={`flowchart LR
    Q["Question"] -- "1. Context relevance:<br/>did we retrieve the right evidence?" --> C["Retrieved context"]
    C -- "2. Faithfulness:<br/>is the answer supported by the context?" --> A["Answer"]
    Q -- "3. Answer relevance:<br/>does it address the question?" --> A`}
/>

| Metric | Question | How to measure | If it fails, fix… |
|---|---|---|---|
| **Context recall / relevance** | Was the needed evidence retrieved (and how much noise came with it)? | recall@k and MRR against labelled chunks (Module 4); or a judge on retrieved chunks | Chunking, hybrid search, reranking, query rewriting |
| **Faithfulness** (groundedness) | Is every claim in the answer supported by the retrieved context? | Number/date code check + faithfulness judge (lesson 4) | Grounding prompt, citations, generation model |
| **Answer relevance** | Does the answer actually address the question? | Judge with a narrow rubric | Prompt, query understanding, refusal logic |
| **Correctness** (needs a reference) | Does it match the known right answer? | Compare with expected properties or a reference answer | Any of the above, so diagnose with the first three |

Libraries such as **RAGAS** and **DeepEval** implement versions of these metrics (context precision/recall, faithfulness, answer relevancy). They're a fast start, but they're still LLM judges, so **calibrate them on your data** (lesson 5) before trusting their numbers.

## Reading the triad: a diagnosis table

| Context recall | Faithfulness | Answer relevance | Diagnosis |
|---|---|---|---|
| Low | — | — | **Retrieval problem.** Generation can't use what isn't there |
| High | Low | — | **Generation problem:** the model ignores or distorts the evidence |
| High | High | Low | **Understanding problem:** a faithful answer to the wrong question (query rewriting, intent) |
| High | High | High | The pipeline works on this case. If users still complain, check the dataset (lesson 3) |

## Evaluating agents: outcome and trajectory

Agents take multi-step paths with tools. Evaluate **both**:

| | Outcome evals | Trajectory evals |
|---|---|---|
| Question | Did the agent achieve the goal? | **How** did it get there? |
| Examples | The refund exists with the right amount; the reply is correct; the database ends in the right state | Right tools called, in a sensible order; no forbidden calls; no duplicate side effects; under the step and cost budget |
| Strength | Tolerant of different valid paths | Catches risky behaviour that happens to end well |
| Weakness | Misses dangerous paths that succeeded | Too strict if you demand one exact path |

Practical trajectory checks are usually **properties**, not exact sequences:

```python
# evals/agent_checks.py
def trajectory_checks(trace: list[dict]) -> dict[str, bool]:
    """trace: [{"type": "tool_call", "name": ..., "input": {...}}, ...] from your agent's logs."""
    calls = [step for step in trace if step["type"] == "tool_call"]
    names = [c["name"] for c in calls]
    refunds = [c for c in calls if c["name"] == "issueRefund"]

    def looked_up_before_refund() -> bool:
        if not refunds:
            return True
        first_refund = names.index("issueRefund")
        return "getShipment" in names[:first_refund]

    return {
        "looked_up_before_refund": looked_up_before_refund(),
        "at_most_one_refund": len(refunds) <= 1,
        "no_forbidden_tools": not set(names) & {"deleteCustomer", "sendBulkEmail"},
        "within_step_budget": len(calls) <= 8,
    }
```

And for outcomes, the most reliable approach is **environment-based evaluation**: run the agent against a sandbox (a test database or mock APIs), then check the **end state** with code (the refund row exists, amount = 340, exactly one row), rather than judging the final text.

<ThinkFirst question="Relay's policy Q&A scores: context recall@5 = 0.92, faithfulness = 0.95, answer relevance = 0.71. Where is the problem, and what would you look at next?">

**The problem is understanding the question, not retrieval or grounding.** The right evidence is retrieved (0.92) and answers stick to it (0.95), but almost 30% of answers don't address what was actually asked.

**Next steps:**

1. **Read the failing cases** (error analysis on the 29%). Typical patterns: multi-part questions where only one part is answered; follow-ups interpreted without conversation context; the model answering a more general question than the one asked.
2. **Check query rewriting** for follow-ups (Module 4), and whether multi-part questions need decomposition.
3. **Check the prompt:** does it tell the model to answer every part of the question, and to ask a clarifying question when the request is ambiguous?
4. **Validate the judge** for answer relevance (calibration, lesson 5). A strict judge can produce low scores too, so confirm with a quick human check on 20 cases.

</ThinkFirst>
