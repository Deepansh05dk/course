<Incident title="Redacted into uselessness" severity="SEV3">
Acme's privacy review required PII redaction before any text reached the model or the logs. The team switched on a redaction library with default settings. The next morning, Relay could no longer look up shipments: the redactor had decided that part of every shipment number looked like a phone number, so the model received `ACM-<REDACTED>`. Support tickets doubled. The guardrail was "working".
</Incident>

**Guardrails** are checks that run around the model: on what goes in, on what comes out, and on tool calls. You've already built the most important ones (the tool policy layer, output filters, canaries). This lesson covers the rest of the toolbox, and how to keep guardrails from becoming the outage.

## PII redaction with Presidio

Microsoft's open-source **Presidio** combines named-entity recognition (spaCy models) with pattern recognizers (emails, phones, IBANs, card numbers) and lets you add your own. Tested:

```python
"""Redact PII before text leaves your boundary (to a model, a log, or a trace)."""
import re

from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_anonymizer import AnonymizerEngine
from presidio_anonymizer.entities import OperatorConfig

analyzer = AnalyzerEngine()  # spaCy NER + built-in pattern recognizers
analyzer.registry.add_recognizer(PatternRecognizer(  # Acme customer numbers are personal data too
    supported_entity="ACME_CUSTOMER_ID",
    patterns=[Pattern("acme customer id", r"\bCUST-\d{2,8}\b", 0.9)],
))
anonymizer = AnonymizerEngine()

ENTITIES = ["PERSON", "EMAIL_ADDRESS", "PHONE_NUMBER", "IBAN_CODE", "CREDIT_CARD", "ACME_CUSTOMER_ID"]
KEEP = re.compile(r"\bACM-\d{4}-\d{6}\b")  # business IDs the agent needs; never redact these


def redact(text: str) -> str:
    keep = [m.span() for m in KEEP.finditer(text)]
    results = [
        r for r in analyzer.analyze(text=text, entities=ENTITIES, language="en")
        if not any(r.start < end and start < r.end for start, end in keep)  # drop overlaps with kept IDs
    ]
    return anonymizer.anonymize(
        text=text,
        analyzer_results=results,
        operators={"DEFAULT": OperatorConfig("replace", {"new_value": "<REDACTED>"}),
                   "PERSON": OperatorConfig("replace", {"new_value": "<PERSON>"}),
                   "EMAIL_ADDRESS": OperatorConfig("replace", {"new_value": "<EMAIL>"})},
    ).text
```

```text
IN : Hi, I'm Maria Gonzalez (CUST-42). Email me at maria.g@example.com or call +1 415 555 0132.
OUT: Hi, I'm <PERSON> (<REDACTED>). Email me at <EMAIL> or call <REDACTED>.
IN : Please refund to IBAN DE89 3704 0044 0532 0130 00, my card 4111 1111 1111 1111 was charged twice.
OUT: Please refund to IBAN <REDACTED>, my card <REDACTED> was charged twice.
IN : shipment ACM-2025-000183 is late, ask for priya
OUT: shipment ACM-2025-000183 is late, ask for priya
```

Two findings from testing this, both typical of real deployments:

1. **The incident above happened here.** Before the `KEEP` rule, the third input came out as `shipment ACM-<REDACTED> is late`: Presidio's phone recognizer matched `2025-000183` (with a score of 0.4). Business identifiers that look like PII need explicit protection, and you need a **test set of your own data** to find them.
2. **It missed "priya".** A lowercase first name without context isn't recognized by the NER model. Redaction **reduces** PII exposure; it doesn't guarantee zero. Design so that a miss isn't catastrophic (access-controlled logs, retention limits).

Where to apply redaction:

| Place | Why |
|---|---|
| **Logs and traces** | The most common leak: prompts with customer data copied into a logging system that half the company can read (Module 9) |
| **Before third-party services** | Evaluation tools, analytics, external APIs that don't need the identity |
| **Before the model** | Only when the model genuinely doesn't need the data. Often it does (it must say the customer's name), so the real control is your contract with the model provider (data retention, training use) |
| **Eval datasets** | Production traces copied into datasets (Module 5) should be redacted or synthetic |

## Safety classifiers and guardrail frameworks

| Tool | What it does | Notes |
|---|---|---|
| **Llama Guard** (Meta, open weights) | An LLM fine-tuned to classify prompts and responses against a safety taxonomy (violence, self-harm, illegal activity…) | Self-hostable; adds a model call; good for content-safety policies |
| **Provider-side safety** | Models' built-in refusals; some providers offer moderation endpoints or classifiers | Free or cheap; not configurable to your business rules |
| **NeMo Guardrails** (NVIDIA, open source) | A framework for defining "rails" (allowed topics, dialogue flows, checks on input, output and retrieval) | Useful for keeping a bot on-topic and orchestrating several checks |
| **Prompt injection classifiers** | Small models that score text for injection likelihood | Cheap first filter; misses obfuscated and novel attacks (lesson 2) |
| **Your own deterministic checks** | Regexes, allow-lists, schema validation, business rules | Fast, predictable, testable. **Usually the most valuable guardrails you'll write** |

A good default stack for a B2B product like Relay: deterministic checks everywhere, PII redaction on logs and traces, an output check for links and leaks, and a safety classifier only where users can steer the model toward harmful content.

## The costs: latency and false positives

Every guardrail has a **cost** that must be measured like a feature:

- **Latency:** a classifier call might add 50–300 ms. Run input guardrails **in parallel** with the model call where possible, and cancel the model call if the guardrail fails.
- **Streaming:** output guardrails must work on chunks (like the canary guard in lesson 2), or you lose streaming.
- **False positives:** a guardrail that blocks 2% of legitimate requests blocks 2,000 customers a day at 100K requests. Measure its precision and recall on a labeled set, exactly like an LLM judge (Module 5).

<ThinkFirst question="Relay is deployed for a healthcare logistics customer shipping medical samples. Their compliance team wants 'guardrails on everything'. Which guardrails do you actually propose, and which do you push back on?">

**Propose:**

- **PII and PHI redaction in logs, traces and eval datasets** (patient names, sample IDs linked to people), with a custom recognizer for their identifiers and a tested allow-list for shipment IDs.
- **Deterministic tool policy** (as in lesson 3) and **output checks**: no external links, canary for prompt leaks, and no patient identifiers in responses to users who aren't authorized.
- **Grounding checks** for answers about handling requirements (temperature limits, hazardous materials), where a wrong answer is dangerous: citations required, refuse when the policy isn't found.

**Push back on:**

- **A general toxicity or safety classifier on every message:** the users are logistics staff, the content is operational, and the false positives would block legitimate messages about "biohazards" and "dangerous goods".
- **Redacting everything before the model:** the model needs shipment details to do its job. The right control there is the data-processing agreement and region choice with the model provider.

Every guardrail you propose should come with its measured latency and false-positive rate.

</ThinkFirst>
