Exact search compares the query with everything. **Approximate nearest neighbour (ANN)** search gives up a tiny bit of accuracy for a huge gain in speed: instead of checking 10 million vectors, it checks a few thousand and *almost always* finds the true neighbours.

The most widely used ANN algorithm in production is **HNSW (Hierarchical Navigable Small World)**. It's in pgvector, Qdrant, Weaviate, Milvus, Elasticsearch/OpenSearch, Redis, and others.

## The intuition: a road network for vectors

Think about driving to a house in another city. You don't check every street. You take a **motorway** to the right region, **main roads** to the right neighbourhood, then **local streets** to the door.

HNSW builds exactly that: a graph where each vector is connected to some of its neighbours, organised in **layers**:

- Every vector exists on **layer 0**. Each vector is also randomly promoted to higher layers with decreasing probability, which gives a few "hub" nodes at the top (like a skip list).
- **Search** starts at the top layer and greedily moves to whichever neighbour is closest to the query, then drops down a layer and repeats, refining at each level. At layer 0 it explores a candidate list of size **`ef_search`** and returns the best k.

## The knobs

| Parameter | What it controls | Higher value means |
|---|---|---|
| **`M`** | Links per node in the graph | Better recall, **more memory**, slower build |
| **`ef_construction`** | Candidate list size while building | Better graph quality, **slower build** |
| **`ef_search`** | Candidate list size while querying | **Better recall, slower queries.** Tunable per query, no rebuild |

`ef_search` is your main production dial: you can raise it for a high-stakes feature and lower it for autocomplete, on the same index.

## Measuring it: recall@k

**Recall@k** = of the true k nearest neighbours (from exact search), how many did the approximate search return? It's the metric you trade against latency.

```python
# evals/vector_bench.py: brute force vs HNSW on clustered unit vectors
import time

import hnswlib
import numpy as np

N, DIM, K, QUERIES = 100_000, 384, 10, 200
rng = np.random.default_rng(42)


def unit(x: np.ndarray) -> np.ndarray:
    return x / np.linalg.norm(x, axis=1, keepdims=True)


# Real embeddings are clustered (topics), not uniform noise, so simulate that.
centers = rng.standard_normal((2_000, DIM), dtype=np.float32)
data = unit(centers[rng.integers(0, len(centers), N)] + 0.6 * rng.standard_normal((N, DIM), dtype=np.float32))
queries = unit(centers[rng.integers(0, len(centers), QUERIES)] + 0.6 * rng.standard_normal((QUERIES, DIM), dtype=np.float32))

# --- exact (brute force): one matrix multiply, then top-k ---
start = time.perf_counter()
scores = queries @ data.T
exact = np.argpartition(-scores, K, axis=1)[:, :K]
brute_ms = (time.perf_counter() - start) / QUERIES * 1000

# --- approximate: HNSW ---
index = hnswlib.Index(space="cosine", dim=DIM)
start = time.perf_counter()
index.init_index(max_elements=N, M=16, ef_construction=200)
index.add_items(data, np.arange(N))
build_s = time.perf_counter() - start

print(f"brute force: {brute_ms:.2f} ms/query (recall 1.000 by definition)")
print(f"HNSW build: {build_s:.1f} s")
for ef in (10, 40, 100, 400):
    index.set_ef(ef)
    start = time.perf_counter()
    labels, _ = index.knn_query(queries, k=K)
    hnsw_ms = (time.perf_counter() - start) / QUERIES * 1000
    recall = np.mean([len(set(labels[i]) & set(exact[i])) / K for i in range(QUERIES)])
    print(f"HNSW ef_search={ef:>3}: {hnsw_ms:.3f} ms/query, recall@{K} = {recall:.3f}")
```

One run of exactly this script (a cloud container, CPU only):

| Method | ms / query | recall@10 |
|---|---|---|
| Brute force (batched matrix multiply) | 1.61 | 1.000 |
| HNSW `ef_search=10` | 0.024 | 0.926 |
| HNSW `ef_search=40` | 0.056 | 1.000 |
| HNSW `ef_search=100` | 0.137 | 1.000 |
| HNSW build time (100K vectors) | 26 s | — |

Notice the trade-offs: queries are about **30× faster** than brute force at full recall, but the index took **26 seconds to build** for just 100K vectors. Build time and memory are the price. And this synthetic data is easy; on real embeddings, expect to need a higher `ef_search` for the same recall. **Run it on your data.**

## Other ANN families (know the names)

| Family | Idea | Where you'll see it |
|---|---|---|
| **IVF** (inverted file) | Cluster vectors; search only the nearest clusters (`nprobe`) | FAISS, pgvector `ivfflat`, Milvus |
| **PQ** (product quantization) | Compress vectors into short codes; approximate distances | FAISS, large-scale systems, often combined with IVF |
| **Disk-based graphs** (e.g. DiskANN-style) | Graph search with vectors on SSD | Very large corpora that don't fit in RAM |

HNSW is the usual default: excellent recall and latency, easy to tune. The main costs are **memory** and **build time**.

<ThinkFirst question="Relay's policy search uses HNSW with ef_search=40 and gets recall@10 of 0.97 on your benchmark. Product wants answers about refunds to be 'as accurate as possible', and autocomplete suggestions in the search box to appear within 50 ms. How do you configure retrieval for both, on one index?">

**Use per-query `ef_search` on the same index:**

- **Autocomplete:** a low `ef_search` (e.g. 10–20) and a small k. Speed matters most and a slightly imperfect suggestion list is harmless. Combine with a prefix/keyword index for exact terms.
- **Refund answers (high stakes):** a higher `ef_search` (e.g. 100–200), a larger candidate set (k = 50), then a **reranker** (Module 4) to pick the best 5. The extra milliseconds are invisible next to LLM latency (seconds).

Then **measure both**: recall and p95 latency per configuration on your real data, and keep a recall canary in production. The broader principle is to **budget accuracy and latency per feature**, not globally.

</ThinkFirst>
