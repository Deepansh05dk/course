<Incident title="Only 2 results, for a question with 40 answers" severity="SEV3">
Relay searched policies with `WHERE region = 'BENELUX'` added to the vector query. After the HNSW index was created, many questions suddenly returned only 1–3 chunks, sometimes zero, even though dozens of matching Benelux policies existed. The answers got thin and refusals spiked. Nothing errored. The index was doing exactly what approximate indexes do with filters.
</Incident>

For most teams, the best first vector database is **the Postgres they already run**. **pgvector** adds a `vector` type, distance operators, and HNSW/IVFFlat indexes. You get transactions, joins, backups, access control and your existing tooling for free.

## Schema

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id               bigserial PRIMARY KEY,
    tenant_id        int         NOT NULL,             -- which customer (Acme, ...)
    document_id      bigint      NOT NULL REFERENCES documents(id),
    region           text        NOT NULL,             -- a filterable attribute
    content          text        NOT NULL,
    embedding        vector(384) NOT NULL,             -- dimension must match the model
    embedding_model  text        NOT NULL,             -- the index contract (lesson 1)
    created_at       timestamptz NOT NULL DEFAULT now()
);

-- Approximate index for cosine distance. Defaults: m = 16, ef_construction = 64.
CREATE INDEX chunks_embedding_hnsw ON chunks
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

Operators (smaller is always "closer"):

| Operator | Distance | Index ops class |
|---|---|---|
| `<=>` | Cosine distance (1 − cosine similarity) | `vector_cosine_ops` |
| `<->` | L2 (Euclidean) | `vector_l2_ops` |
| `<#>` | **Negative** inner product | `vector_ip_ops` |

## Querying from Python

```python
# app/retrieval.py
import numpy as np
import psycopg
from pgvector.psycopg import register_vector

conn = psycopg.connect("postgresql://relay@localhost/relay", autocommit=True)
register_vector(conn)  # lets psycopg send and receive numpy arrays as vectors


def search(query_vec: np.ndarray, tenant_id: int, k: int = 5) -> list[tuple]:
    return conn.execute(
        """
        SELECT id, content, 1 - (embedding <=> %(q)s) AS similarity
        FROM chunks
        WHERE tenant_id = %(tenant)s
        ORDER BY embedding <=> %(q)s
        LIMIT %(k)s
        """,
        {"q": query_vec, "tenant": tenant_id, "k": k},
    ).fetchall()
```

The `ORDER BY embedding <=> … LIMIT k` shape is what lets Postgres use the HNSW index. Check with `EXPLAIN ANALYZE` that it really does.

## The filtering pitfall

This is the incident above. With approximate indexes, **filtering happens after the index scan**. The HNSW scan returns its best `ef_search` candidates (40 by default), and *then* the `WHERE` clause removes the ones that don't match. If only 10% of rows match the filter, you get about 4 results on average, however many matching rows exist.

<Diagram
	caption="Post-filtering: the index finds the nearest 40 overall, then the filter throws most of them away."
	code={`flowchart LR
    Q["Query + WHERE region='BENELUX'"] --> I["HNSW scan<br/>best 40 candidates overall<br/>(ef_search = 40)"]
    I --> F["Filter: region = BENELUX<br/>(about 10% match)"]
    F --> R["about 4 rows returned<br/>even if 400 match in the table"]`}
/>

Fixes, from pgvector's own guidance:

```sql
-- 1. Iterative index scans (pgvector 0.8.0+): keep scanning until enough rows pass the filter.
SET hnsw.iterative_scan = relaxed_order;   -- or strict_order
SET hnsw.max_scan_tuples = 20000;          -- upper bound on work (the default)

-- 2. A bigger candidate list for this query only.
BEGIN;
SET LOCAL hnsw.ef_search = 200;
SELECT ... ORDER BY embedding <=> $1 LIMIT 5;
COMMIT;

-- 3. Few distinct filter values: a partial index per value.
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WHERE (region = 'BENELUX');

-- 4. Selective filters (matching a small % of rows): a normal B-tree on the filter column,
--    so Postgres can do exact search over the few matching rows instead.
CREATE INDEX ON chunks (region);
```

## Multitenancy and permissions

For FDE work this matters most. Two rules:

1. **Isolation for recall and speed:** with one shared approximate index, one big tenant's vectors affect recall and speed for everyone. pgvector's guidance is **list partitioning by tenant** (or separate tables):

```sql
CREATE TABLE chunks (/* ...columns... */) PARTITION BY LIST (tenant_id);
CREATE TABLE chunks_acme PARTITION OF chunks FOR VALUES IN (1);
-- each partition gets its own HNSW index
```

2. **Isolation for security:** the tenant and permission filter must be **enforced by the data layer**, never added by the LLM, and never optional. Use Postgres **row-level security** or a mandatory query-builder parameter, and test it. A missing `WHERE tenant_id = …` is a data breach, not a relevance bug. (Permission-aware retrieval is covered fully in Module 4.)

## Operating it

| Concern | What to do |
|---|---|
| **Build time** | Builds are much faster when the graph fits in `maintenance_work_mem`. Build after bulk-loading, not row by row during a big import |
| **Memory** | Best performance when the index fits in RAM. Check size with `pg_relation_size`; use `halfvec` to halve it |
| **Dimensions** | `vector` indexes support up to 2,000 dims, `halfvec` up to 4,000. Bigger models need half precision, binary quantization, or shortened vectors |
| **Updates and deletes** | Dead tuples reduce result counts and quality. Vacuum regularly; consider periodic `REINDEX ... CONCURRENTLY` for heavy churn |
| **Model changes** | Blue/green: add a new column (or table) for the new model's vectors, backfill, index, evaluate, switch reads, then drop the old one |
| **Recall** | Keep a recall canary (lesson 4) running against production |

## pgvector or a dedicated vector database?

| Choose **pgvector** when… | Consider **a dedicated vector DB** (Qdrant, Weaviate, Milvus, Pinecone, …) when… |
|---|---|
| Up to roughly tens of millions of vectors | Hundreds of millions to billions of vectors |
| You already run Postgres and want one system | Vector search is the core product and needs its own scaling |
| You need joins, transactions, and row-level security with your business data | You need advanced built-in features (native hybrid search, multi-vector, quantization tuning, filtering-aware graph search) |
| The customer's security team already approves Postgres (very common in FDE work) | The team is happy to run (or buy) another piece of infrastructure |

The honest default: **start with pgvector, and measure.** Switch when a measured limit (latency, recall under filters, scale, operational cost) appears, not because of a blog post.

## 🧪 Module 3 lab: Relay's vector store

Build it in your `relay` repo, with Postgres + pgvector in Docker (the `pgvector/pgvector` image). **Acceptance criteria:**

1. **Schema** with `tenant_id`, `embedding_model`, and a fixed dimension; an HNSW cosine index.
2. **Ingestion script** that embeds at least 5,000 chunks (any public text works until Module 4 brings the real policy PDFs), in batches, with retries, storing the model name per row.
3. **`search(query, tenant_id, k)`** with a mandatory tenant filter, enforced by row-level security or a required parameter, plus a **test** that a query for tenant A can never return tenant B's chunks.
4. **Benchmark notebook:** exact search (no index) vs HNSW at 3 `ef_search` values, reporting recall@10 and p95 latency on your real embeddings.
5. **Filtering experiment:** a filter matching about 10% of rows, with and without `hnsw.iterative_scan`. Report result counts.
6. **Startup assertion:** the app refuses to start if the configured embedding model differs from the model stored in the index.
7. `docs/module-3.md`: your recall/latency chart, the chosen settings with justification, the memory estimate at 10× your data, and three things that surprised you.

<ThinkFirst question="An enterprise customer (FDE engagement) has 25 business units. Documents must only be visible to employees of the owning unit, plus a few 'company-wide' documents visible to all. Search must stay fast and accurate. Design the pgvector data model and query path.">

A strong design separates **security** from **performance**, and makes security impossible to skip:

1. **Data model:** each chunk carries `unit_id` (or NULL for company-wide) and inherits document-level ACLs at ingestion. Permissions are copied from the source system and **re-synced** when they change there.
2. **Enforcement:** Postgres **row-level security** keyed on the session's unit (set per request from the authenticated user, never from the LLM or the prompt). Every search runs under that policy, so a forgotten `WHERE` can't leak data.
3. **Performance:** list-partition by `unit_id` (25 partitions, each with its own HNSW index), plus a small partition for company-wide documents. A query searches the user's partition plus the company-wide one, then merges. Each search is over a small, dense, unfiltered index, which gives good recall with no post-filtering trap.
4. **Tests:** automated tests that impersonate users from different units and assert no cross-unit results, run in CI.
5. **Audit:** log which chunk IDs were retrieved for which user, so you can answer "who saw what".

The underlying principle: **performance tricks are optional; permission enforcement is not.**

</ThinkFirst>
