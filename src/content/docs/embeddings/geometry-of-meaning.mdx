## Text as coordinates

An **embedding model** turns a piece of text into a list of numbers, a **vector** with typically 384 to 3,072 dimensions. The model is trained so that texts with **similar meaning end up close together** in that space, even when they share no words.

<Diagram
	caption="Each text becomes a point. Closeness means similar meaning. Real spaces have hundreds of dimensions, which this 2-D sketch flattens."
	code={`flowchart LR
    A["'I want my money back'"] --> E["Embedding model"]
    B["'Refunds are paid within 10 days'"] --> E
    C["'Box arrived smashed'"] --> E
    E --> V1["[0.12, -0.83, 0.07, ...]"]
    E --> V2["[0.10, -0.79, 0.11, ...]"]
    E --> V3["[-0.66, 0.21, 0.45, ...]"]
    V1 -. "close: same meaning" .- V2
    V1 -. "far: different topic" .- V3`}
/>

**Semantic search** then becomes geometry: embed the query, find the stored vectors closest to it, and return their texts. That's the "R" in RAG.

Things to notice (try each one):

1. **"my money back"**: the semantic column finds refund policies without sharing the word "refund". Keyword search finds almost nothing.
2. **"opening times"**: semantic search finds the support-hours snippet; keyword search finds nothing at all.
3. **"ERR_AUTH_8091"**: the embedding can't handle it (this demo's vocabulary has never seen the code), while **keyword search nails it**. Modern subword models *can* embed such codes, but they tend to blur them with similar-looking strings. Exact identifiers are keyword territory.
4. **"tax on imported goods"**: semantic search puts the right answer second, behind a wrong one. Embeddings are good at "roughly the right neighbourhood", not perfect ranking. That's why production systems add **hybrid search and reranking** (Module 4).
5. **Compare two sentences:** "refunds are allowed…" vs "refunds are not allowed…" have very high similarity. **Negation barely moves the vector.** Real embedding models do better than this demo, but still not reliably.

:::

## Embedding in code

```python
# Every major provider and open-source library has the same shape:
#   list of texts in -> list of vectors out
from sentence_transformers import SentenceTransformer  # open-source, runs locally

model = SentenceTransformer("all-MiniLM-L6-v2")        # 384 dimensions
vectors = model.encode(
    ["Refunds are paid within 10 business days.", "I want my money back"],
    normalize_embeddings=True,                           # unit length, so dot product = cosine
)
print(vectors.shape)                                     # (2, 384)
print(float(vectors[0] @ vectors[1]))                    # cosine similarity
```

Hosted APIs (OpenAI, Voyage, Cohere, Google, Mistral, …) work the same way: send a batch of texts, get vectors back. Some models also distinguish **query** embeddings from **document** embeddings (an input-type flag or a prefix). Use them as documented, because mixing them up quietly hurts retrieval.

## Choosing an embedding model

| Factor | Why it matters |
|---|---|
| **Retrieval quality on your data** | Public leaderboards (like MTEB) are a starting filter. Build a small retrieval eval (Module 4) and test 2–3 models |
| **Languages** | A great English model can be poor in Hindi or German. Test every language your users write in |
| **Dimensions** | More dimensions means more storage and memory per vector and slower search. Some models support shortening vectors with small quality loss |
| **Max input length** | Text beyond the limit is silently truncated, so long chunks lose their ending |
| **Cost and latency** | You embed every document once (and again on every re-index), plus every query |
| **Hosting and data** | API vs self-hosted: privacy, data residency, and air-gapped customers (very common in FDE work) |
| **Domain** | Legal, medical and code have specialized models that can beat general ones |

## The index contract

The most important operational fact about embeddings:

> **Vectors from different models (or different versions of a model) are not comparable.**

A query embedded with model B searched against documents embedded with model A returns garbage, **silently**: the system still returns results with similarity scores, they're just meaningless. So:

- Store the **model name and version** next to every vector.
- Changing the model means **re-embedding everything** (plan the cost and time).
- Re-index with a **blue/green** approach: build the new index alongside the old one, evaluate, then switch traffic atomically.

<ThinkFirst question="Acme's agents ask questions in English, but 30% of the policy documents are in Dutch and German. How would you design and test the embedding setup?">

1. **Choose a multilingual embedding model** whose training covers English, Dutch and German, so that an English query lands near a Dutch passage with the same meaning (cross-lingual retrieval).
2. **Build a cross-lingual retrieval eval:** 50+ English questions whose correct answer lives in Dutch or German documents, plus same-language controls. Measure recall@5 for 2–3 candidate models.
3. **Compare against alternatives:** translate documents to English at ingestion time (more cost and a translation-error risk, but simpler retrieval), or translate queries into each language and merge results.
4. **Keep keyword search per language** for exact terms (product names, codes), with language-aware tokenization.
5. **Answer in the agent's language**, with the citation pointing to the original-language source (and a translated excerpt).

The core lesson: **test the languages you actually serve**, because models that are excellent in English can quietly fail elsewhere.

</ThinkFirst>
