A **deep-research engine** takes a hard question ("How are Antwerp port delays affecting European container shipping costs this month, and what are carriers doing about it?"), searches the web and internal sources for minutes, reads dozens of pages, and writes a structured report where every claim is cited. Several AI products offer this. Building one well touches almost every module of this course: agents (6), retrieval and grounding (4), evals (5), security (8), cost control (10).

This case study designs one from scratch, with diagrams for every layer and tested code for the parts that don't need a model.

## 1. The design problem

| Requirement | Why it's hard |
|---|---|
| **Answers questions no single page answers** | Needs decomposition, many searches, and synthesis across sources |
| **Every claim is verifiable** | Citations must point to the actual supporting text, not just a plausible URL |
| **Current information** | Search results and caches must respect freshness; old pages must not pose as new |
| **Minutes, not hours; cents, not dollars** | Fan-out multiplies cost and latency; it needs budgets |
| **The web is hostile** | SEO spam, contradictory sources, and pages containing prompt injections |
| **Millions of users** | Rate limits, abuse, crawling etiquette, and caching across users |

The design separates three kinds of work with very different needs:

| Component | Needs | Model choice |
|---|---|---|
| **Planner** | Judgment: what to look for, when to stop | Strong model, moderate effort |
| **Readers** | Volume: dozens of pages, extract what matters | Small, fast, cheap model; **no tools** |
| **Synthesizer** | Reasoning across sources, careful writing | Strong model, higher effort |
| **Search, ranking, fetching, verification** | Determinism, speed | Code, not models |

## 4. Planning: decomposition and stopping

The planner turns one question into **independent sub-questions** that can be researched in parallel, and decides when enough is enough.

- **Clarify when ambiguous.** "Costs" could mean spot rates, contract rates or surcharges. A short clarifying question (or explicit assumptions in the report) beats an hour of research on the wrong thing.
- **Plan for parallelism.** Sub-questions should be answerable independently; dependent steps ("find the top carriers, then their surcharges") become a second round.
- **Iterate on gaps.** After a round, the planner looks at the notes: which sub-questions lack sources, where do sources conflict? It schedules targeted follow-ups, within the budget.
- **Stop deliberately.** Stopping rules: every sub-question has at least two independent sources, or the budget is spent, or a round adds nothing new. Without explicit rules, research agents either stop too early or never stop (Module 6's circuit breakers).

## 5. Search and fetch at scale

**Searching.** Several queries per sub-question, phrased differently (Module 4's query transforms), with date filters when freshness matters. Internal sources (a company's documents) can be searched in the same step through retrieval tools.

**Fetching.** Pages are fetched in parallel, with timeouts, retries, and **politeness**: respect robots rules and rate limits per domain, identify your crawler, and cache. A **page cache** keyed by canonical URL saves cost and load when many users research similar topics, with a TTL that depends on the page type (news: hours; reference pages: days).

**Cleaning.** Strip navigation, ads and boilerplate; keep headings, tables, publication date and author. A cleaned page is often a fraction of the raw HTML's tokens.

If you build on the Claude API, server-side tools can do the searching and fetching for you, with citations in the response:

```python
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    tools=[
        {"type": "web_search_20260209", "name": "web_search", "max_uses": 8,
         "blocked_domains": ["seo-farm.example"]},
        {"type": "web_fetch_20260209", "name": "web_fetch", "max_uses": 15,
         "citations": {"enabled": True}},
    ],
    messages=[{"role": "user", "content": question}],
)
```

Web fetch only fetches URLs already present in the conversation (from the user or from search results), which also limits how far an injected instruction could send data. That's the fastest way to a working prototype. At scale, many teams own the pipeline themselves (their own search provider, page cache, readers and verifier) to control cost, freshness, source policy and latency. The architecture in this case study is that "own the pipeline" version.

## 6. Ranking and selecting sources

Search results contain duplicates (the same page with tracking parameters), stale pages, many pages from one site, and spam. Selection is deterministic code, tested here:

```python
"""Core pieces of a deep-research engine that don't need a model: dedupe, source selection, citation checks."""
import re
from collections import Counter
from dataclasses import dataclass
from datetime import date
from urllib.parse import parse_qsl, urlencode, urlsplit, urlunsplit

TRACKING = {"utm_source", "utm_medium", "utm_campaign", "utm_term", "utm_content", "gclid", "fbclid", "ref"}


def canonical_url(url: str) -> str:
    """Same page, same key: lowercase host, no 'www.', no fragment, no tracking params, no trailing slash."""
    parts = urlsplit(url.strip())
    host = parts.netloc.lower().removeprefix("www.")
    query = urlencode(sorted((k, v) for k, v in parse_qsl(parts.query) if k.lower() not in TRACKING))
    path = parts.path.rstrip("/") or "/"
    return urlunsplit(("https", host, path, query, ""))


@dataclass
class Source:
    url: str
    title: str
    domain_quality: float     # 0-1, from your own allow/deny lists and past reliability
    relevance: float          # 0-1, from a reranker (Module 4)
    published: date | None


def select_sources(candidates: list[Source], k: int, today: date, max_per_domain: int = 2,
                   max_age_days: int | None = None, min_quality: float = 0.3) -> list[Source]:
    """Pick up to k good sources: deduplicated, fresh enough, not all from one domain, never junk."""
    seen, per_domain, chosen = set(), Counter(), []
    def score(s: Source) -> float:
        return 0.6 * s.relevance + 0.4 * s.domain_quality
    for s in sorted(candidates, key=score, reverse=True):
        key = canonical_url(s.url)
        domain = urlsplit(key).netloc
        too_old = max_age_days is not None and (s.published is None or (today - s.published).days > max_age_days)
        if key in seen or per_domain[domain] >= max_per_domain or too_old or s.domain_quality < min_quality:
            continue
        seen.add(key)
        per_domain[domain] += 1
        chosen.append(s)
        if len(chosen) == k:
            break
    return chosen


def _norm(text: str) -> str:
    return re.sub(r"\s+", " ", text).strip().lower()


def verify_citations(answer_claims: list[dict], pages: dict[str, str]) -> list[dict]:
    """Each claim cites a source URL and a supporting quote. Check that the quote really is in that page."""
    report = []
    for c in answer_claims:
        page = pages.get(canonical_url(c["url"]))
        if page is None:
            status = "cited page was never fetched"
        elif _norm(c["quote"]) in _norm(page):
            status = "ok"
        else:
            status = "quote not found in page"
        report.append({"claim": c["claim"], "status": status})
    return report
```

```text
canonical: {'https://port-antwerp.example/news/congestion'}
  picked: Port update            https://port-antwerp.example/news/congestion
  picked: Berth schedule         https://port-antwerp.example/news/berths
  picked: Wait times rise        https://shipping-news.example/antwerp-wait-times
  ok                           <- Waits rose to 3.4 days
  ok                           <- Waits are 3-4 days
  quote not found in page      <- Waits will fall next month
  cited page was never fetched <- Strike caused it
```

What the test showed, before and after one fix:

- Three spellings of the same URL (`www.`, tracking parameters, a fragment, `http`) collapse to **one** canonical key, so the page is fetched and cited once.
- The first version had no quality floor. It picked **"10 Shocking Antwerp Delays"** from an SEO farm as the 4th source: the per-domain cap had (correctly) skipped the third and fourth port pages, and the spam page's high relevance score carried it in. With `min_quality` it now returns three good sources instead of padding to four with junk. **Diversity rules need a quality floor**, or they actively promote spam.
- The undated carrier advisory was excluded by the 30-day freshness rule: when freshness matters, an unknown date is treated as old.

Source quality itself comes from your own policies: allow and deny lists, past reliability, primary sources (the port authority) over aggregators, and per-topic trust lists.

## 7. Reading: small models, no tools

Readers process each page into **notes**: a claim, an **exact quote** that supports it, the URL, and the publication date. Two design choices make this layer safe and cheap:

1. **Small model.** Readers do extraction, not reasoning. A small model is fast and cheap, and the notes are far shorter than the pages, so the synthesizer's context stays small (see the calculator below).
2. **No tools, constrained output.** Web pages are untrusted content, and some contain prompt injections. The readers are **quarantined** (Module 8's dual-LLM pattern): they can only return notes in a fixed schema, so an injected instruction can at worst become text in a note, never an action. The synthesizer only ever sees notes.

## 8. Citation-grounded synthesis and verification

The synthesizer writes from notes only, and every factual sentence must cite one. Then **code verifies** before the user sees anything:

- Each cited quote must appear (after normalizing whitespace and case) in the fetched page text. In the test above, an invented quote ("expected to fall in November") is caught, and so is a citation to a page that was never fetched.
- A failed check sends the sentence back to the synthesizer to fix or drop. Never ship unverified citations: a fake citation is worse than no citation, because it borrows the source's credibility.
- **Conflicts are reported, not resolved silently:** "The port reports an average wait of 3.4 days; trade press reports waits of up to 5 days." Show source dates next to claims so readers can judge freshness.

Quote verification checks that the quote **exists**; it doesn't check that the quote **supports** the claim. That second check is an LLM judge's job (Module 5), run on a sample of reports or on high-stakes claims.

## 9. Cost and latency control

The levers:

| Lever | Effect |
|---|---|
| **Budgets** (searches, pages, tokens, wall-clock time) per request | Hard caps; the planner works within them |
| **Small-model readers** | Turn many long pages into short notes; the strong model reads notes, not pages |
| **Page cache** across users | Popular topics are fetched once |
| **Early stopping** | Stop when sub-questions are covered, not when the budget runs out |
| **Effort per stage** | Moderate for planning, higher for synthesis, low for readers |
| **Tiered products** | A quick answer by default (few sources, seconds); deep research when the user asks for it |
| **Streaming progress** | Show the plan, sources found and partial findings while it works (Module 2), so 2 minutes feels productive |

## 10. Abuse and safety at scale

- **Prompt injection from the web:** quarantined readers, no tools on untrusted content, citations verified by code (sections 7–8).
- **SEO spam and manipulation:** quality floors, deny lists, preferring primary sources, and requiring independent corroboration for important claims.
- **Harmful research requests:** the same safety policies as the rest of the product, applied to the question **and** the plan (a harmless-looking question can decompose into harmful sub-searches).
- **Crawling ethics and load:** robots rules, per-domain rate limits, caching, and identifying your crawler.
- **Cost abuse:** per-user rate limits and budgets (Module 9's gateway), and detection of automated use.
- **Privacy:** research about private individuals deserves policies of its own; logs of research questions are sensitive data.

## 11. Evaluating a research engine

| Metric | How |
|---|---|
| **Citation precision** | Share of citations whose quote exists **and** supports the claim (code + judge) |
| **Citation coverage** | Share of factual sentences that have a citation |
| **Factual accuracy** | Expert-written reference answers for a fixed question set; judge plus human spot checks |
| **Completeness** | Did the report cover each aspect the reference answer lists? |
| **Freshness** | For time-sensitive questions: are the newest relevant facts included? |
| **Cost and latency** | Per question, per tier; p50 and p95 |

Freshness makes evals tricky: reference answers expire. Keep a stable set (historical questions with frozen sources) for regression testing, and a rotating set of current questions with fresh references.

## 13. Trade-offs at a glance

| Decision | Option A | Option B | This design |
|---|---|---|---|
| Who searches and fetches | Provider's server tools | Your own pipeline | Prototype with server tools; own the pipeline at scale |
| Who reads pages | The strong model | Small-model readers | Small readers with no tools, notes with quotes |
| Synthesis context | Full pages | Notes | Notes (cheaper, safer, citable) |
| Citation checking | Trust the model | Code verification + judge sampling | Code for existence, judge for support |
| Depth | Fixed | Planner decides within budgets | Planner + budgets + stopping rules |

## 14. Build your own mini version

A version you can build in a weekend, using the course's pieces:

1. **Planner:** one call with structured outputs returning 3–5 sub-questions (Module 1).
2. **Search and fetch:** the API's web search and fetch tools, or a search API plus `httpx` with a page cache.
3. **Selection:** `canonical_url` and `select_sources` from above.
4. **Readers:** a small model with structured outputs returning `{claim, quote, url, published}` notes, run with bounded concurrency (Module 10).
5. **Synthesizer:** notes in, cited report out.
6. **Verifier:** `verify_citations`, with one repair round.
7. **Evals:** 20 questions with reference answers; citation precision, coverage and accuracy (Module 5).

<ThinkFirst question="Acme wants this engine for internal use: 'research our customers before account reviews', across the web AND internal CRM notes and contracts. What changes in the design?">

1. **Permissions:** internal sources must be retrieved with the requesting employee's permissions (Module 4's permission-aware retrieval). A sales rep shouldn't see contract terms for accounts they don't own.
2. **Trust levels:** internal documents and web pages are both untrusted text for injection purposes (CRM notes can be written by customers, Module 8), but internal sources are usually **more authoritative** on facts about the customer. Rank them first and label them distinctly in the report.
3. **Data flow:** internal data must not leak into web searches (a search query containing confidential contract terms is a data leak to the search provider). The planner generates web queries from public facts only, enforced by a check.
4. **Citations to internal documents** link to the source system, respecting access controls when clicked.
5. **Evals** include per-account reference briefings written by account managers, and checks that no confidential detail appears in web-search logs.
